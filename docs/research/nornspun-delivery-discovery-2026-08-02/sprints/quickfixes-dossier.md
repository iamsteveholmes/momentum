# Sprint Dossier: The Two Quickfixes — `quickfix-consolidate-shared-ui-viewmodels` and `quickfix-epic-story-taxonomy-migration`

**Date:** 2026-08-02
**Role:** Discovery agent for the nornspun delivery-discovery investigation — dossier on the two named quickfixes, covering intent / plan / execution / claim / reality-in-git / aftermath / user-capability verdict for each, plus what their existence says about the practice.

---

## Executive summary

1. **Both quickfixes' `.momentum/sprints/quickfix-*/` directories are fossils, not source of truth.** Each contains only an empty `specs/` folder with one `.feature` file, frozen at creation time. Neither directory was ever updated again — the actual execution for both happened elsewhere (a bundled sprint for one, a directly-logged worktree run for the other). Evidence: `git log --all -- .momentum/sprints/quickfix-*` shows only the May 3 bulk path-migration commit touching either path; the ViewModel quickfix's frozen `.feature` file diverges from the version that was actually used (see #3).
2. **The taxonomy migration (`epic-story-taxonomy-migration`, run as `quickfix-2026-04-07`) executed cleanly and fast** — worktree open to merge to AVFL-validated completion in under an hour (19:22–20:19 on 2026-04-07), 4 commits, 61 files changed, 7 AVFL findings with 4 resolved inline. It is the healthier of the two specimens.
3. **The ViewModel quickfix (`quickfix-2026-04-11`) was never run standalone.** Its Gherkin spec was "copied" into a 3-story sprint (`sprint-2026-04-12`) that also planned two unrelated backend stories (LLM cost logging, model quality eval). That sprint's `sprint-dev` **hung in Phase 7 after merging to main**; the developer manually finished closure bookkeeping four days later (commit `740d85d`, 2026-04-16). The frozen quickfix-directory spec still contains 4 SilenceToggle persistence scenarios that were removed from the *live* spec copy before execution — proof the quickfix directory was abandoned mid-flight rather than consciously archived.
4. **The taxonomy migration's core acceptance criterion — "no story key uses a D/C-number prefix, every `depends_on` resolves" — has been silently violated for ~4 months and is still violated today.** Story `d4-14-end-to-end-session-loop-integration-test` (status `done` in the index) was created **one day after** the migration closed, using the pre-migration naming convention, with 4 `depends_on` entries (`d4-1-...`, `d4-2-...`, `d4-4-...`, `d4-5-...`) that point to slugs which no longer exist anywhere in `stories/index.json` — verified live in the current repo state, not historical. The one-time migration fixed the existing backlog but installed no forward guardrail; drift returned within 24 hours and was never caught.
5. **That same story's core deliverable does not exist in the codebase it claims to touch.** D4.14's own Dev Agent Record documents building `tests/integration/test_session_loop_full_cycle.py` plus a full backend memory-loop stack (campaigns router, session repos, Urd/Verdandi memory tools) on 2026-04-09 — but `git log --all` in the real `nornspun-backend` repo returns **zero** hits for that filename, ever. The work was committed into a stale, non-canonical embedded copy of the backend (`nornspun/nornspun-backend/`, "Tree B") nested inside the planning-hub repo, not the real repo (`~/projects/nornspun-backend`, "Tree A").
6. **That directory confusion is independently documented and dated by the project's own ASR-003 assessment** (`docs/assessments/asr-003-urd-agent-drift-directory-confusion-2026-05-28.md`): Tree B's "last `src` activity" was ~April 9 — the exact date of the D4.14 commit — and Tree B was deleted on 2026-05-29 (commit `dbc8615`) after a pre-removal sweep found no CI/build reference to it. **Nobody checked whether D4.14's specific test needed porting to Tree A before deletion**; ASR-003's own blast-radius review cleared ~17 *other* "done" backend stories as not-suspect but never named D4.14. The story's "done" status (and a second inconsistency: the story file itself still reads `Status: review`, not `done`) has stood unchallenged since.
7. **The functionality D4.14 claimed to prove end-to-end in April is, per the mission's own sprint-2026-07-13 dossier context, still not done in July.** `features.json` lists `session-capture` and `session-prep` — the exact loop D4.14's AC1–AC5 exercise (campaign creation → adventure upload → Urd capture → bind → Verdandi prep) — as `status: partial` (1/2 and 2/3 stories done respectively), and the three sprint-2026-07-13 memory stories (`episode-transcript-persistence-store-a`, `urds-post-session-capture`, `episode-close-summarization-store-b`) sit at `status: review`, not `done`, as of this writing. The same capability has apparently been attempted at least twice (April, July) without a durable end-to-end win.
8. **The Silence Toggle — built during the ViewModel-consolidation lineage — is a mirror-image failure mode: a feature that worked but was never wanted.** `SDR-005` (amended 2026-06-09) records the product owner's verdict: *"I never wanted to see it again... a model invention during planning that was never wanted."* The toggle's ViewModel/AppPrefs code is exactly what `consolidate-shared-ui-viewmodels` migrated to `commonMain` — real engineering effort spent consolidating a feature that was rejected before the consolidation quickfix even ran (SilenceToggle's UI call-sites were deleted from `MainWindow.kt`/`MainActivity.kt` in the *same story*, and its Gherkin scenarios were pulled from the live spec — see #3).
9. **The ViewModel consolidation itself held up correctly.** Unlike the taxonomy migration's drift, `AppPrefs.kt`, `SilenceViewModel.kt`, and `AmbientCompletionSignalViewModel.kt` remain singly-defined in `shared/commonMain` today, referenced correctly from both Android and Desktop call sites, never touched again since the 2026-04-11 commits. The Ambient Completion Signal (the surviving, wanted half of that story) is live and wired on both platforms.
10. **What the existence of these two "quickfixes" says about the practice:** they show the practice using the quickfix lane for two structurally different things — (a) a genuine single-purpose planning-artifact migration that ran clean and fast (taxonomy), and (b) an ad-hoc engineering refactor that got folded into a full sprint mid-flight and inherited that sprint's orchestrator failure (ViewModel consolidation). Neither the quickfix registry (`sprints/index.json` → `quickfixes[]`, one entry) nor the sprint-log directory (`sprint-logs/quickfix-2026-04-07/`, one entry — for the *other* quickfix) agree with each other or with the frozen `.momentum/sprints/quickfix-*/` directories on which quickfix ran when or how. The bookkeeping trail for "quickfix" as a category is itself inconsistent across at least four different record systems.

## Body

### A. `quickfix-epic-story-taxonomy-migration` (registry name for the run: `quickfix-2026-04-07`)

#### Intent

Story `epic-story-taxonomy-migration.md` (created 2026-04-07, commit `a5979b4`): rename the numbered delivery-phase taxonomy (`epic-d1`…`epic-d8`, `epic-c1`…`epic-c3`; story slugs like `d3-10-norn-switch-clears-chat`) to descriptive, non-numbered slugs matching the Momentum format used elsewhere. Explicitly scoped as **pure planning-artifact restructuring, no application code changes**. Nine (later expanded) tasks: design epic taxonomy (with a developer-approval gate), design story slug mapping, write `slug-migration-map.json`, rewrite `epics.md`, rekey `stories/index.json`, `git mv` story files, update `sprints/index.json`, rename sprint spec `.feature` files, validate.

#### Plan

Gherkin spec (`epic-story-taxonomy-migration.feature`, 13 scenarios) written same day (commit `7905259`), then amended after an AVFL checkpoint pass before dev (commit `4d2f297`, "address AVFL checkpoint findings"): added a sprint-spec-rename scenario (F-01), a slug length/uniqueness scenario (F-02), an idempotency clause (F-03), a PRD-note assertion (F-04), added `architecture.md`/`prd.md` to the story's `touches[]` (F-05), and — notably — **excluded the migration's own ad-hoc story from its own integrity checks** (F-06), to avoid the migration checking itself against itself before it existed.

#### Execution

Sprint-log `.claude/momentum/sprint-logs/quickfix-2026-04-07/impetus.jsonl` (4 lines, verbatim):
```
19:22:51 — Worktree created for epic-story-taxonomy-migration, specialist: dev
20:09:11 — Story epic-story-taxonomy-migration merged to main — 4 commits, 61 files changed
20:19:05 — Validation complete: 7 findings, 4 resolved (1 high, 2 medium, 1 low)
20:19:21 — Quickfix quickfix-2026-04-07 completed
```
Total elapsed time worktree-open to quickfix-complete: **57 minutes**. The post-merge AVFL fix commit (`62945a0`, 20:18:57) shows what was and wasn't fixed: renamed 5 sprint spec files that were missed in `sprint-2026-04-06` (F-HIGH, fixed), removed stray NFR refs from `epics.md` (F-MED, fixed), transitioned the story's own status to done (F-MED, fixed), updated a stale `touches` path for `global-silence-toggle` (F-LOW, fixed). **4 of 7 findings resolved — the other 3 are not itemized in any commit message and their disposition is not recorded** (see Open Questions).

#### Claim vs. reality-in-git

The story's Gherkin ACs claim, among others: "no key matches the pattern of a D-number or C-number prefix," "every `depends_on` reference points to an existing story," "every `epic_slug` value resolves to a defined epic." Checked against the **current** `stories/index.json` (302 entries, 2026-08-02):

- `epic_slug` integrity: **clean.** Zero entries match `epic-d[0-9]` / `epic-c[0-9]` (verified via `re.match` scan of all 302 `epic_slug` values).
- Story-key prefix integrity: **one violation.** `d4-14-end-to-end-session-loop-integration-test` still carries the old-style key.
- `depends_on` integrity: **broken by the same story.** Its 4 `depends_on` entries (`d4-1-verdandi-agent-session-prep-conversations`, `d4-2-adventure-ingestion-feed-the-living-memory`, `d4-4-urds-post-session-capture`, `d4-5-living-memory-the-loop-connects`) are **all dangling** — none exists as a key in the current index (verified by direct lookup).

Root cause, established by commit timestamps: the migration's own commit closed at `2026-04-07T20:19` (Apr 7 evening). Story `d4-14-end-to-end-session-loop-integration-test` was created the **next day**, `2026-04-08T17:04:19-07:00` (commit `536bc41`), using the pre-migration naming scheme for both its own key and its dependency list — meaning whoever/whatever created it did not consult the just-completed rename map for stories it depended on (those dependency targets had already been renamed to descriptive slugs by the time this story was written). This is a one-shot migration with no standing enforcement: it fixed ~100 pre-existing entries in an hour, but nothing prevented the very next story from reintroducing the exact defect it removed, and no subsequent validator — across ten further sprints and two more quickfixes — has caught it. Also worth flagging: `d4-14-...`'s own `stories/index.json` entry says `"status": "done"`, but the story file itself (`d4-14-end-to-end-session-loop-integration-test.md`) is header-stamped `**Status:** review` — a live status mismatch between the index and the story file, undetected for the same ~4 months.

#### A downstream discovery reached via this dangling reference: the D4.14 story and the "Tree B" directory trap

Pulling the `d4-14-end-to-end-session-loop-integration-test` thread (it is *the* stray old-style story key the taxonomy migration missed) surfaced a second, independently significant and independently documented finding:

- The story's own Dev Agent Record (commit `0065661`, 2026-04-09, message: *"test(backend): D4.14 end-to-end session loop integration test"*) states plainly: *"Backend skeleton had no D4 implementation (D4.2, D4.4, D4.5 marked done in stories/index.json but code not present). Implemented minimum viable backend infrastructure needed for test to compile and run."* — i.e., the dev agent discovered at the time that three **other** "done" stories had no corresponding code, and built a stopgap backend (campaigns router, session models, memory tools, Verdandi tools, `test_session_loop_full_cycle.py`, 24 files) to make its own test runnable.
- That commit (`0065661`) lives in the **planning-hub `nornspun` repo**, under a path `nornspun-backend/...` — because at the time, the planning-hub repo still contained a nested, non-canonical copy of the backend.
- **Verified absence in the canonical repo:** `git log --all --oneline -- "*test_session_loop_full_cycle*"` run directly inside `~/projects/nornspun-backend` returns **zero results** — the file has never existed in the real backend's git history. `find . -iname "test_session_loop*"` in that repo likewise returns nothing; `tests/integration/` there contains only `test_challenge_behavior.py`.
- **The project's own assessment confirms the mechanism.** `docs/assessments/asr-003-urd-agent-drift-directory-confusion-2026-05-28.md` documents "Tree A" (canonical, separate repo `~/projects/nornspun-backend`) vs. "Tree B" (a stale embedded stub at `~/projects/nornspun/nornspun-backend/`, not its own git repo, "last `src` activity ~Apr 9" — the exact date of the D4.14 commit). ASR-003's own purpose was to retract an earlier false claim that the Urd agent was drift/never-built (it wasn't — that claim itself was an artifact of reading Tree B by mistake per a misleading `CLAUDE.md` line). Its **Recommendation 1** — delete Tree B, fix `CLAUDE.md` — was actioned the same cycle: commit `dbc8615` (2026-05-29) removed 39 tracked files from Tree B after "a pre-removal sweep confirmed no active CI/run/build config referenced the nested path." That sweep checked for *build* references, not for *unmigrated dev-agent work* — it did not ask whether any Tree-B-only commit needed porting to Tree A before deletion. D4.14 is such a commit, and it was not named anywhere in ASR-003's blast-radius review (which cleared ~17 *other* stories as "not suspect" because their `touches[]` files do exist in Tree A — D4.14's do not, and it isn't on that list).
- Net effect: `d4-14-end-to-end-session-loop-integration-test` is marked **done**, its own file says **review**, its `depends_on` list is **dangling**, and its sole concrete deliverable — the file that would prove the end-to-end session loop actually works — **does not exist in the repository that runs**. This has been the case, undetected, for roughly four months.
- **This maps directly onto the mission's central hypothesis.** `features.json` currently marks `session-capture` (`status: partial`, 1/2 stories done) and `session-prep` (`status: partial`, 2/3 stories done) — the exact capability D4.14's ACs exercise (campaign creation → adventure upload → Urd capture/bind → Verdandi prep). The sprint-2026-07-13 stories covering the same loop (`episode-transcript-persistence-store-a`, `urds-post-session-capture`, `episode-close-summarization-store-b`) are at `status: review`, not `done`, per the current `stories/index.json`, roughly 3.5 months after D4.14 first claimed (inaccurately, per the above) to have proven the loop end-to-end.

#### Aftermath / user-capability verdict for the taxonomy migration

The taxonomy rename itself is durable and largely correct — a genuine, low-risk, well-executed quickfix for what it directly touched (naming). But it produced no forward-looking guardrail, so its central promise ("every key is descriptive, every dependency resolves") is **currently false** for at least one live "done" story, and chasing that one violation is what surfaced the Tree-A/Tree-B confusion — a separate, larger, and independently-confirmed episode of real engineering work (a working test + a stopgap backend implementation) being silently lost for over a month before anyone noticed, and never reconciled even after it was noticed.

### B. `quickfix-consolidate-shared-ui-viewmodels` (registered as `quickfix-2026-04-11`)

#### Intent

Story `consolidate-shared-ui-viewmodels.md` (created 2026-04-11, commit `8c322cd`, ad-hoc epic): after an earlier `shared-ui-consolidation` story moved UI components/screens to `commonMain` but explicitly excluded ViewModels (citing "hard platform dependencies"), this story re-audits that exclusion and finds it overbroad — `AppPrefs`, `SilenceViewModel`, `AmbientCompletionSignalViewModel`/`CompletedTask` can also move to `commonMain`, while `ChatViewModel`, `NornSelectorViewModel`, `AppStateViewModel` genuinely stay platform-specific. Goal: eliminate duplicate ViewModel maintenance surfaces (the stated motivating bug: a `UrdTextPrimary` title-color divergence between platforms).

#### Plan

Gherkin spec written for the quickfix (`.momentum/sprints/quickfix-consolidate-shared-ui-viewmodels/specs/consolidate-shared-ui-viewmodels.feature`): 6 scenarios — 4 for SilenceToggle ON/OFF persistence across Android/Desktop restarts, 2 for Ambient Completion Signal fire/dismiss on Android/Desktop.

#### Execution — the quickfix was never run standalone

The quickfix directory's frozen spec is a **fossil**: `git log --all -- .momentum/sprints/quickfix-consolidate-shared-ui-viewmodels/` shows no commits touching it after its creation except the May 3 bulk path migration (`8bb9e15`, a pure directory move from `_bmad-output/implementation-artifacts/` — content unchanged). Instead:

- Commit `72d45bc` (2026-04-12, *"create sprint-2026-04-12 with Gherkin specs for all 3 stories"*) states the consolidate-shared-ui-viewmodels `.feature` file was **"copied from quickfix sprint"** into a full sprint alongside two unrelated stories: `llm-cost-logging-and-usage-tracking` and `model-quality-evaluation-framework`.
- Before dev started, the live copy was edited (commit `1ee7f2b`, 2026-04-12): the 4 SilenceToggle persistence scenarios were **removed** from the sprint's copy, with an inline comment: *"toggle was intentionally removed from the app UI in a prior sprint... Remove these Gherkin scenarios so validators don't flag absence as a regression."* This edit was **never applied to the frozen quickfix-directory copy**, which still has all 4 toggle scenarios today — direct, checkable proof the quickfix directory was abandoned in-place rather than consciously retired (`diff` between the two files, run 2026-08-02, shows exactly this divergence and nothing else).
- Commit `740d85d` (2026-04-16, four days after the sprint activated): *"Sprint-dev hung in Phase 7 after merging to main; closure bookkeeping never ran. All 6 sprint stories are fully implemented... This commit completes the bookkeeping that Phase 6 + Phase 7 would have done."* The developer manually transitioned 6 stories `review → verify → done`, hand-wrote/committed Dev Agent Record sections (Agent Model, Debug Log, Completion Notes, File List) that had been "left uncommitted mid-sprint," and marked the sprint completed with `retro_run_at: null` — i.e. the sprint never got its own retrospective. The quickfix that started as a single-story, same-day fix ended up needing four extra days and manual developer intervention to close.

#### Claim vs. reality-in-git

Despite the process friction, the actual ViewModel migration work checks out cleanly:

- Story's Debug Log References note: *"Confirmed pre-existing state: Tasks 1-4 already committed to `main` branch via commits `eb27297`, `9b9eabe`, `82eda16`, `d17f4e3`, `4946248`"* — verified in `nornspun-client`: all 5 commits land 2026-04-11, 21:08–21:21 (about 1.5–2 hours after the story spec was written at 19:31), linear on `main`, no merge conflicts, matching the story's own File List exactly (created: `shared/commonMain/.../AppPrefs.kt`, `SilenceViewModel.kt`, `AmbientCompletionSignalViewModel.kt`, `androidMain/AndroidAppPrefs.kt`, `desktopMain/JavaPrefsAppPrefs.kt`, `commonTest/InMemoryAppPrefs.kt` + moved tests; deleted: the old per-platform duplicates).
- **Current-state verification (2026-08-02):** exactly one copy of each migrated file exists, all under `shared/src/commonMain/kotlin/com/nornspun/ui/viewmodel/` — no duplicate `AppPrefs.kt` anywhere else in the repo. `SilenceViewModel` is correctly referenced from `MainActivity.kt` (Android) and `MainWindowTest.kt` (Desktop tests); `AmbientCompletionSignal(` is called from both `MainActivity.kt` and `MainWindow.kt`. This part of the story's claim is accurate and has held for nearly four months without regression.
- **The Silence Toggle itself, however, is dead code shipped by the same lineage.** `docs/decisions/sdr-005-silence-toggle-ui-removed.md` (originally 2026-04-14, amended 2026-06-09) records the toggle as **"permanently rejected as a feature, not deferred"** — the product owner's own words: *"I never wanted to see it again"* and *"the feature was a model invention during planning that was never wanted."* `SilenceToggle(` (the composable) has **zero call sites** anywhere in `nornspun-client` today (verified by grep across all non-build `.kt` files) — it exists in `shared/commonMain/ui/components/SilenceToggle.kt` but is never invoked. `SilenceViewModel` likewise has no toggle UI to drive it; it survives only because it was migrated into the shared module, not because the feature is live. This is the practice's "capability that works but isn't wanted" counterpart to the mission's "capability that's claimed but doesn't work" hypothesis — real engineering time (the AppPrefs/SilenceViewModel consolidation) was spent partly in service of a feature the product owner had already/soon-after rejected.

#### Aftermath / user-capability verdict for the ViewModel consolidation

The ViewModel-layer refactor itself is a genuine, durable win — no drift, no duplication regrowth, correctly wired on both platforms. But (a) it never ran as an isolated quickfix — it was absorbed into a 3-story sprint whose orchestrator hung post-merge, forcing four days of manual closure by the developer and skipping that sprint's retro entirely (`retro_run_at: null`), and (b) roughly half its Gherkin surface (the SilenceToggle scenarios) targeted a feature later declared permanently unwanted — meaning the quickfix's own acceptance criteria, as originally scoped, could never have been meaningfully "passed" in a way a real user would recognize as valuable, because the toggle they were testing was headed for deletion regardless of test outcome.

### C. What the existence of these two quickfixes says about the practice

- **The quickfix lane is used for structurally different problems without a shared execution guarantee.** The taxonomy migration is a self-contained, low-blast-radius planning-doc rewrite that ran in under an hour with its own worktree and AVFL pass — a clean fit for "quickfix." The ViewModel consolidation is a multi-file, cross-platform code refactor that, in practice, got folded into a regular multi-story sprint the moment a second and third unrelated story showed up needing the same Gherkin-authoring pass — "quickfix" as a *label* did not protect it from sprint-scale process failure (the Phase-7 hang).
- **Bookkeeping about "what even is a quickfix" disagrees with itself across four separate record systems**, discovered independently in this investigation:
  1. `.momentum/sprints/index.json → quickfixes[]` lists exactly one entry (`quickfix-2026-04-11` / consolidate-shared-ui-viewmodels) — it does not list the taxonomy migration at all.
  2. `.claude/momentum/sprint-logs/` has exactly one quickfix log directory (`quickfix-2026-04-07/impetus.jsonl`) — for the taxonomy migration, the one *missing* from list (1).
  3. `.momentum/sprints/quickfix-*/` (the two directories this dossier was asked to audit) exist for both, frozen at creation, and are stale for at least one of them (see the SilenceToggle-scenario diff in Section B).
  4. The actual work landed via a bundled 3-story sprint (`sprint-2026-04-12`, for the ViewModel item) and a standalone worktree run outside any of the above four systems (for the taxonomy item, per its own sprint-log).
  No single artifact, read alone, tells a future reader which record is authoritative for either quickfix — this dossier had to cross-reference all four plus two downstream repos to reconstruct what happened.
- **A "quickfix" completing (even AVFL-validated, even fast) does not guarantee its acceptance criteria stay true.** The taxonomy migration is the stronger of the two runs by every process metric (single hour, dedicated worktree, logged decisions, 4/7 findings resolved same-session) — and it is precisely this quickfix whose core guarantee is currently, verifiably broken in production data, because "done" here meant "true at the moment of the AVFL pass," not "enforced going forward."
- **Both quickfixes, chased to their roots, surface the same failure shape the mission hypothesis names: passing artifacts (a merged migration, a merged refactor, a "done" index entry, an AVFL PASS) that do not correspond to a working, wanted, or even *present* piece of user-facing functionality** — the dangling D4.14 test, the vanished Tree-B backend work it depended on, and the rejected Silence Toggle the ViewModel work partly served, are three independent instances of that same pattern found by following two quickfixes that most people would assume are minor, low-stakes housekeeping.

## Counter-evidence & falsifiability

Evidence that cuts against the framing above, and what would overturn it:

- **The taxonomy migration's damage is small in absolute terms.** Of 302 current stories, exactly 1 violates the "no D/C-prefix key" rule and exactly 1 story has dangling `depends_on` entries (the same story, 4 dangling refs to itself). This is a ~0.3% defect rate on the artifact the migration produced, not systemic failure of the rename itself. If a reader wants to argue the migration "worked," 301/302 clean keys four months later, with zero `epic_slug` violations, supports that reading.
- **The ViewModel consolidation code is unambiguously good work.** No regressions, no duplication regrowth, clean single-source in `commonMain`, both platforms wired correctly, ~4 months with zero drift. If the question is narrowly "did this refactor accomplish its stated technical goal," the answer is yes.
- **The Tree-B directory confusion was self-corrected by the practice, not by this investigation.** ASR-003 is a real, dated, adversarially-verified assessment the project produced on its own (2026-05-28/29), including a documented refutation methodology (6 evidence readers → 3 skeptics → synthesis) and a same-cycle fix. This is evidence the practice *can* catch and correct serious drift/confusion — it just didn't catch the specific D4.14 test-file loss within that otherwise-thorough pass, and nothing has caught it since (this dossier is the first record of it, as far as searches below could determine).
- **It is possible D4.14's missing test was later superseded by different, non-identically-named coverage** rather than genuinely lost. This dossier did not find such coverage (`tests/integration/` in `nornspun-backend` has only `test_challenge_behavior.py`), but did not exhaustively audit every backend test file for equivalent end-to-end assertions under a different name/location — see Open Questions.
- **The "3 unresolved AVFL findings" for the taxonomy migration** (7 found, only 4 itemized as resolved in the fix commit) could mean either 3 were resolved without being itemized in the commit message, or 3 were silently dropped. This dossier could not distinguish these from the available commit messages alone (see Open Questions) — treat the "3 unresolved" framing as a gap, not a confirmed silent-drop.

**What would prove the core finding wrong:** discovery of a commit or file in `~/projects/nornspun-backend` implementing `test_session_loop_full_cycle.py` (or a materially equivalent full-cycle integration test) under any name, at any point in that repo's history — this dossier's search (`git log --all` for the filename, plus a listing of `tests/integration/`) found none.

## Open questions

- **The 3 unresolved AVFL findings from the taxonomy migration's post-merge validation** (7 found, 4 itemized as fixed in commit `62945a0`) — their content and disposition are not recorded in any commit message, sprint log, or file this dossier located. Could not determine whether they were fixed without documentation, deferred, or dropped.
- **Whether `d4-14-end-to-end-session-loop-integration-test`'s dangling `depends_on` list has ever been flagged by any later validation pass** (AVFL, sprint-planning, retro) in the ten sprints since April. No retro-transcript-audit or ledger entry mentioning this slug was found in the ledger (`.momentum/practice-ledger.jsonl`) or the sprint-2026-07-13 audit extracts, but those extracts were only lightly sampled for this dossier, not exhaustively grepped for every historical story slug.
- **Whether the Tree-B-only backend work (campaigns router, memory tools, `NornDeps`, `test_data` router, etc.) was ever independently rebuilt in Tree A under different commit messages**, making the *functional* loss smaller than the *literal file* loss suggests. Spot checks (`get_npc_encounters`, `get_unfinished_business`, `_bind_memories_impl`, `search_adventure_content`) show equivalent-sounding functions do exist in the current `nornspun-backend` `verdandi.py`/`memory.py` — but this dossier did not diff their implementations against the lost Tree-B versions to determine if they are faithful reimplementations, partial reimplementations, or coincidentally-named different designs. This matters for how much of the "lost work" was truly wasted versus redone through the normal backlog.
- **Why `sprints/index.json`'s `quickfixes[]` array has exactly one entry and it is the *less well-documented* of the two runs** (the ViewModel one, which was folded into a sprint) while the better-documented run (taxonomy, with its own sprint-log) is absent from that registry — no commit or doc explains this asymmetry; it may simply predate the registry field's introduction or reflect a manual, incomplete backfill.
