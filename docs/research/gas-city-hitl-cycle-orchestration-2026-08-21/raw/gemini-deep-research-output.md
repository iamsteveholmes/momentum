Research Report: Gas City Human-in-the-Loop Gates and Multi-Phase Cycle OrchestrationExecutive SummaryThe transition from localized, single-session artificial intelligence coding assistants to distributed, multi-agent software factories represents a critical inflection point in modern engineering operations. Gas City, extracted from the monolithic architecture of the earlier Gas Town project, serves as an orchestration-builder Software Development Kit (SDK) specifically designed to facilitate this transition. By externalizing workflow state into persistent tracking units and decoupling execution from human interactive sessions, Gas City enables the automation of complex, multi-phase software engineering lifecycles.   As of August 21, 2026, the Gas City ecosystem operates on the stable v1.4.0 release. The introduction of the "Formulas v2" production controls has fundamentally altered how Directed Acyclic Graphs (DAGs) are evaluated, fanned out, and governed across a fleet of CLI coding agents such as Claude Code. However, fully autonomous execution is rarely desirable in production environments where security, architectural integrity, and financial burn rates are paramount. Consequently, orchestrators must provide robust mechanisms to halt autonomous execution and await human verification—a paradigm known as Human-in-the-Loop (HITL) gating.   This comprehensive analysis investigates Gas City's current capabilities for orchestrating multi-phase engineering cycles (Triage → Planning → Build → Retrospective) that rely on mandatory human approval gates. The research systematically evaluates the platform's native [steps.gate] mechanisms, the emergent engineering patterns utilized to capture human verdicts, the notification infrastructure required to alert operators, and the operational maturity of the platform and its underlying persistence layer. The findings indicate that while native declarative human gates remain partially nascent in their strict vocabulary implementation, the platform provides immensely powerful convergence mechanisms, check loops, and observation dashboards that successfully facilitate enterprise-grade human approval workflows.1. Architectural Foundations of Gas City v1.4.0To accurately assess the implementation of human approval gates and multi-phase orchestration, it is essential to first understand the foundational object model that governs Gas City's state machine. The orchestrator is built upon six irreducible primitives, designed to ensure that the system relies strictly on state persistence rather than ephemeral in-memory flags.   Table 1 delineates the core primitives that form the basis of all HITL workflows.PrimitiveDefinition and Operational FunctionAgentThe configured worker (e.g., Claude Code, Codex) that executes assigned tasks. Under the legacy v1 model, formulas were executed in-process within a single interactive session, tightly coupling the orchestrator to the agent's lifespan. The v2 paradigm, which is enabled by default in the city.toml daemon configuration (formula_v2 = true), separates control from execution.   In the v2 architecture, the orchestrator's control dispatcher owns the execution graph. It independently executes "control beads"—operations responsible for checking dependencies, executing retries, managing parallel fan-outs, and draining queues—while the configured external agents execute the actual "work beads". This bifurcation means that a formula no longer runs as a monolithic script but rather as a persistent bead tree known as a "molecule". Consequently, gating a formula effectively means instructing the control dispatcher to pause the expansion of the DAG until a specific state transition occurs within the bead store. This Erlang/OTP-inspired supervision model ensures that human approvals are treated as immutable state transitions within the database, providing robust crash-recovery and auditability.   2. Gate Mechanics and the [steps.gate] PrimitiveThe orchestration of a software factory requires explicit chokepoints where automated parallel fan-outs can be halted for human verification. The [steps.gate] primitive was conceptualized to serve as this declarative roadblock within a formula's TOML definition.The Status of the Gate VocabularyAccording to the foundational Gas City specifications, the [steps.gate] table was designed to support multiple blocking types, explicitly identifying human, timer, gh:pr, and mail as valid gate types. However, forensic analysis of the current August 2026 release cycle confirms that explicit, first-class implementation of these declarative gate types within bundled community formulas remains largely limited to doc-comments and experimental branches.   There are currently zero bundled formulas shipping in the primary registry (hosted at https://github.com/gastownhall/gascity-packs) that utilize a naked type = "human" in a [steps.gate] block without relying on auxiliary convergence logic. Issue #620 specifically addresses the implementation of the "human gate (and any other step that parks sessions on human gates)," illustrating that while the framework's internal/convergence/formula.go engine parses the gate constructs, the platform relies heavily on variable-driven check loops to enforce blocking behavior safely.   The rationale for this architectural delay stems from Gas City's core design principles, specifically the mandate to "Keep judgment out of Go". The framework is designed strictly to move work, not to reason about it. A monolithic "wait-for-human" node type executed by the Go controller risks infusing the transport layer with stateful judgment logic. Instead, the maintainers favor paradigms where the human is treated identically to an agent actor, meaning the gate is simply a work unit assigned to a human that blocks subsequent nodes in the DAG.   Blocking Edges and Dependency GraphsDespite the nascent state of a dedicated type = "human" keyword, the control dispatcher inherently supports absolute blocking edges through the DAG's standard dependency graph. In Gas City, beads declare dependencies via a BLOCKS and Needs relationship.   When a formula step is dispatched, the orchestrator instantiates it as a bead within a larger tracking container known as a "convoy". If a specific bead in that convoy is assigned to a human actor, or left unassigned but tagged with a rigorous review label, the orchestrator's fan-out logic will strictly quarantine all downstream steps. The control dispatcher continuously evaluates the readiness of nodes during its reconciliation tick. Because the prerequisite bead remains in an OPEN state, the dispatcher refuses to instantiate the subsequent dependent steps.   Manual Closure and Transient Read FixesThe resolution of this blocking edge requires explicit human intervention. A human operator must manually intervene—using the command line interface (gc bd close <id>) or the visual dashboard—to transition the blocking bead's status from OPEN to CLOSED. Only upon this manual closure does the control dispatcher unblock the downstream convoy and resume the automated agent fan-out.   Historically, gates and control routing suffered from severe race conditions under heavy concurrent load, leading to dispatcher wedges. A critical architectural improvement in the v1.4.0 release is the introduction of highly resilient retry and drain mechanisms. Attempting to spawn or fan-out immediately after a gate closure no longer quarantines an in-flight run due to momentary configuration read failures. The control dispatcher will intelligently retry transient config reads rather than failing closed, which makes manually closing a human gate a significantly more reliable and deterministic operation than in the previous v1.2.x era.   3. Human Verdict and HITL Implementation PatternsGiven the architectural constraints and design philosophies surrounding the [steps.gate] primitive, practitioners have coalesced around highly specific design patterns to enforce "Approve," "Iterate," or "Reject" decisions. These patterns leverage the internal/convergence/ bounded iterative refinement loops to treat human feedback as executable state.   The Bounded Check Loop PatternThe most prominent methodology for HITL integration in Gas City is the "Check Loop," often referred to internally as the "ralph-loop". Rather than pausing a single linear step and waiting for a boolean toggle, formulas implement a bounded cycle where an agent attempts a task, synthesizes an artifact, and explicitly submits it for review.   The nature of this review converges based on launch variables passed to the formula, specifically review_mode and interaction_mode.   Autonomous Mode: An adversarial agent (e.g., a dedicated security or architectural review persona) critiques the work without human involvement.Interactive Mode: The loop exits the autonomous agent boundary and assigns a review bead directly to the human operator.   When operating in interactive mode, the human verdict is captured not just as a boolean approval, but as rich bead metadata. If the human operator rejects the proposed work, they do not simply fail the workflow; they append written feedback to the bead's description or metadata payload and reset the status to OPEN, or they generate a new sibling "revision" bead linked via the ParentID.   The convergence engine reads this verdict-as-metadata, detects the delta between the requested state and the current state, and initiates another refinement pass by the agent. The agent's next prompt is dynamically hydrated with the human's specific critique. This pattern ensures that all qualitative judgment remains localized entirely within the persisted bead state, preventing the Go orchestration layer from needing to parse arbitrary textual verdicts.   Explicit Step Assignment and Mail-to-Human ParadigmsBeyond bounded check loops, advanced multi-phase pipelines utilize the Mail subsystem for explicit out-of-band human approvals. In Gas City, inter-agent messaging—including messages directed at human operators—is constructed using the underlying bead persistence layer via TaskStore.Create(bead{type:"message"}).   When a multi-phase cycle reaches a critical, non-reversible juncture—such as a deployment readiness check, a database migration execution, or a production release—the formula generates a mail bead explicitly assigned to the human operator. The human receives this via the Dashboard's Mail interface. The subsequent formula steps are gated strictly on the resolution of this mail bead. If the human replies with an approval payload, the orchestrator detects the state change and triggers the downstream execution order.   The community pr-pipeline pack exemplifies this disciplined approach. The pack provides automated steps to map a change's blast radius and self-review outgoing pull requests against an 11-category scorecard. However, it establishes a hard, non-negotiable "pre-push gate" that strictly refuses to push code or open a PR autonomously. It mandates a manual human initiation for the final deployment step, demonstrating how packs successfully enforce safety boundaries even in highly automated environments.   4. "Silent failures" where an agent waits indefinitely for human input are a primary failure mode in multi-agent orchestration. Multi-Phase Cycle Orchestration and Harness RecipesThe orchestration of a multi-phase engineering cycle—flowing continuously from Triage, to Planning, to Build, and finally to Retrospective—relies on the seamless chaining of distinct formulas and orders. Gas City's architecture is optimally positioned to support this continuous cycle through its rich pack ecosystem, leveraging event-driven triggers to maintain momentum across phase boundaries.   Constructing the Cycle via Orders and TriggersOrders in Gas City act as the dispatch directives. They are triggered by specific conditions, including cron (schedules), cooldown (intervals since the last run), condition (shell exit codes), manual (explicit invocations), and crucially, event (specific system events occurring). To chain distinct phases, an operator configures event-triggered orders that listen for the completion of one phase to instantiate the next.   Triage Phase: An external event—such as a GitHub webhook parsed by an optional gh integration—triggers an initial order. This order launches an intake formula. Packs like gstack provide an explicit "Office-hours intake" stage specifically designed for this purpose, where raw requests are standardized into actionable formats.   Planning Phase: Upon completion of the triage bead, the orchestrator emits a status change event. A subsequent order, configured to listen for this specific epic-triaged event, triggers the planning formula. The bmad pack (Document-first delivery) excels in this phase, executing PRD generation, architectural design, and deep story decomposition.   The Human Gate: Before transitioning to the highly parallelized, high-burn-rate build phase, the bmad pack enforces a mandatory "readiness gate". The DAG halts. The human operator reviews the generated epics and architectural documents. Only upon the human closing this readiness bead does the system proceed.   Build Phase: The closure event of the readiness gate triggers the bmad-build formula, fanning out story-by-story implementation. This phase leverages parallel agent execution with built-in self-checks and acceptance audits.   Retrospective Phase: Triggered via a cron order or upon the closure of a massive epic convoy, a retrospective formula evaluates the cycle. Formulas from the build-basic pack, for instance, generate a factory-run.md summary artifact detailing the successes, failures, and bottlenecks of the run.   Claude Code Harness RecipesThe effectiveness of these multi-phase cycles relies heavily on the underlying execution engine. Gas City natively integrates with CLI coding agents through its "Provider" abstraction, heavily supporting Claude Code (claude -p).   To harness Claude Code as the primary agent runtime, the operator begins by ensuring the Claude CLI is installed and authenticated on the host PATH. During initialization, the operator registers Claude against the built-in preset using gc init --default-provider claude. This scaffolds the required configurations within city.toml:   Ini, TOML[workspace]

Gas City's hook installation process automatically drops provider-specific configuration files into the project's working directories. When a formula routes work to Claude, Gas City dynamically spawns a managed session (typically via tmux or subprocess), injects the prompt, and monitors execution.   A critical enhancement in the recent v1.4.0 release completely resolved historic stall issues associated with Claude's Model Context Protocol (MCP) trust sequences. Previously, managed Claude sessions could hang indefinitely on the interactive "New MCP server found in this project" prompt when their working directory contained an .mcp.json file. Gas City now applies preventive settings projection and a startup-dialog fallback to ensure headless, non-interactive tmux agents can bypass these prompts and reach a ready state reliably, ensuring that multi-phase cycles are not silently wedged by third-party CLI updates.6. Beads Backend Requirements and Operational CostsThe foundation of Gas City's reliability, and its ability to persist human verdicts across sessions, is its persistence layer: the Beads store. Every unit of work, mail message, formula molecule, and organizational convoy is externalized to this database.   GC_BEADS=file vs. Native DoltGas City natively supports two primary backend paradigms, each catering to vastly different operational scales.The File Backend:
By setting the environment variable GC_BEADS=file or defining [beads] provider = "file" in the city.toml configuration, operators can bypass the default database entirely. This file-based store requires zero additional dependencies (obviating the need for dolt, bd, or flock), making it highly advantageous for lightweight, ephemeral CI runs or single-user local experiments. However, it suffers from severe file-lock contention during massive agent fan-outs and lacks native query capabilities.   The Dolt Backend (Default):
For production, multi-agent, distributed orchestration, the bd (beads) provider backed by Dolt is strictly required. Dolt provides a Git-for-data Multi-Version Concurrency Control (MVCC) model, enabling transactional lifecycle semantics, bounded cached reads, and highly concurrent store-aware routing. This backend requires Dolt version 2.1.0 or newer; Gas City actively rejects older builds because releases prior to 1.86.2 lack critical upstream deadlock fixes that can hang synchronization routines under heavy write loads.   Operational Costs and Dolt Bloat Recovery (#1094)Running the Dolt backend in a production factory incurs significant operational overhead, primarily regarding storage management. The most prominent risk is severe database bloat, extensively documented in issue #1094, where a real-world installation rapidly filled a 244GB disk.   The root cause of this bloat was architectural. Working-memory artifacts generated during a formula's iterative refinement loops (e.g., highly detailed, multi-kilobyte system design prompts) were being stamped entirely into each member's user prompt during a parallel fan-out. Because Dolt tracks every granular modification with Git-like historical fidelity, duplicating a massive context payload across fifty sub-agents for every iteration loop caused exponential data bloat within the .dolt directory.   The architectural resolution involved hoisting these bulky, shared payloads into a molecule-scoped file (/artifacts/<molecule-id>/context/) written exactly once. The numerous roster members are then configured to reference this artifact merely by path, drastically reducing the data footprint. For operators encountering legacy bloat from older formulas, the documentation provides strict dolt-bloat-recovery runbooks. Engineering teams deploying Gas City must remain vigilant regarding storage telemetry and actively prune dead branches to maintain Dolt performance.   8. Strategic Conclusions and RecommendationsGas City v1.4.0 is exceptionally fit for orchestrating multi-phase engineering cycles with mandatory human approval gates, provided the systems architect understands the platform's architectural nuances and persistence requirements. It successfully elevates autonomous coding agents from single-session conversational tools into a highly scalable, observable software factory.Based on this exhaustive analysis, the following actionable recommendations are provided for implementing HITL orchestration within Gas City:Do not rely on naked type = "human" primitives. Because the explicit gate type vocabulary remains largely unproductized and relies heavily on experimental branches, architects should design formulas using interaction_mode = interactive and "Check Loop" DAG topologies. By parsing human feedback via bead metadata modification, the system reliably achieves the exact same HITL outcome while maintaining strict state synchronization and adhering to the "Keep judgment out of Go" philosophy.   Standardize on the Gas City Dashboard for HITL operations. The React-based SPA available in v1.4.0 is highly stable, secure (implementing CSRF and CSP protections), and vastly superior to CLI workflows for filtering the noise of multi-agent fan-outs. Operators should be required to monitor the "Mail" and "Beads" views to unblock readiness gates efficiently.   Adopt bmad for Document-First Cycles. If the organizational goal is a strict triage → planning → build → retrospective pipeline, the community bmad (Document-First Delivery) pack, available at https://github.com/gastownhall/gascity-packs, provides the most rigorous out-of-the-box readiness gates and adversarial review structures available in the ecosystem.   Enforce Dolt 2.1.0+ and Monitor Storage Bloat. Use the Dolt backend for all production workflows to ensure transactional integrity during massive fan-outs. However, organizations must strictly implement the artifact-path-referencing pattern defined in #1094 to avoid catastrophic disk bloat, and maintain active alerts on the .dolt directory size.   Prepare for Orchestration v3 Migration. While the Formulas v2 execution logic is sound, architects should limit the complexity of custom pack.toml imports. When Orchestration v3 is released, the explicit [[exports]] namespace resolution will likely break deeply nested legacy import hierarchies, requiring significant refactoring for over-engineered local configurations.   By leveraging persistent work beads, deterministic control loops, and comprehensive UI observability, engineering teams can safely and reliably inject critical human judgment into the heart of parallelized AI workflows using Gas City.

### Q2: Claude Code harness recipe + long-running exec steps

Based on current maintainer guidance and release notes, here are the answers to your questions:Harness Recipe for Claude Code Runtime
Gas City uses long-lived, headless interactive sessions managed via tmux rather than per-step claude -p print-mode invocations. The platform is specifically designed to manage interactive pool sessions, to the point where the v1.3.4 and v1.4.0 releases contain explicit logic to bypass interactive menus that stall headless agents. By applying settings projections and startup-dialog fallbacks, Gas City forces these managed tmux sessions to automatically navigate Claude Code's interactive prompts—such as the "New MCP server found in this project" prompt—so they can reliably reach a ready state. If an execution runs past this limit, the supervisor will terminate it with a context deadline exceeded error. Operators historically bypassed this by hardcoding large maximum timeouts (like 600s or 1200s). Session Lifecycle Boundaries: Under the Formulas v2 controls introduced in recent releases, session lifecycle management operates entirely through a unified worker boundary. This means that waking, resuming, draining, closing, and recovering orphaned sessions all behave based on the persisted state of the work queue, rather than depending on provider-specific timeouts or shortcuts.  Storage Timers: There are also underlying strict constraints for the database execution layer. For instance, the system enforces a strict 60-second context timeout on certain CLI exec wrapper commands, and ephemeral reads are bounded by 30-second timeouts.
