01Do workflows loop? Yes — natively.

A workflow script is plain JavaScript. while, for, and recursion all work, and the tool ships three canonical loop shapes that map exactly onto what you described. A validate-fix loop isn't a workaround in workflows — it's the headline pattern.

  • loop-until-cleanYour QA / review → fix cycle.  while (findings.length && round < cap) { fix; re-verify }
  • loop-until-dryYour AVFL.  Keep finding + fixing until K consecutive rounds surface nothing new — catches the long tail a fixed counter misses.
  • loop-until-budgetDepth scaling.  Scale rounds to a token target: while (budget.total && budget.remaining() > 50_000) { … }

Every loop you named — dev/QA/review/fix, AVFL, e2e/fix — is a natural workflow loop.

02The one constraint that shapes everything

A workflow runs autonomously, in the background, to completion. It cannot pause to ask a human anything. There is no AskUserQuestion, no <ask>, no approval gate inside a workflow. It fans out, loops, returns structured data, and notifies you.

Governing principle
A workflow can only own a span of work between two human gates. The human gates carve sprint-dev into autonomous segments; each segment is a workflow. The skill is the conductor that runs at the gates.

The current workflow.md is shot through with gates — that scatter is exactly why it feels clunky as a workflow today:

  • Phase 3 — Retry / Skip / Halt on dev failure
  • Phase 4 — acknowledge AVFL findings
  • Phase 4c — fix / defer queue decision
  • Phase 4d — accept remaining findings
  • Phase 5 — address team-review findings
  • Phase 6 — verification checklist ·  Phase 7 — push to main

Seven-plus stop-and-ask points. The rebuild's real move: collapse the gates to one at the end — replace "stop and ask at every phase" with "iterate autonomously to a quality bar, review everything once." Your described flow already does this. That's what makes workflows fit.

03Mapping your flow

Because there's no human gate until the report, almost the entire execution span can be one autonomous workflow (optionally composed of sub-workflows via workflow(), one level deep). The skill shrinks to a conductor with a single human loop.

This loop can't be in a workflow — every iteration gates on human judgment.

3.1The execution workflow — sketch

// EXECUTION WORKFLOW — launched by the skill, runs to completion, returns a data model
phase('Build')
const built = await pipeline(readyStories,
  s    => agent(devPrompt(s), { agentType: s.devAgent, schema: DEV_RESULT }),  // custom momentum agent
  done => qaReviewFixLoop(done),   // while !clean && round<cap: parallel(QA, review) -> fix -> re-verify
)

phase('Integrate')
const { merged, conflicts } = sequentialMerge(built)   // auto-merge; conflicts collected, NOT halted

phase('AVFL')
const avfl = await workflow('avfl-sprint', { diff, acs })   // loop-until-dry, its own saved workflow

phase('E2E')
const e2e = await e2eValidateFixLoop({ ... })   // replaces TeamCreate (see §04)

phase('Report')
const reportPath = await agent(reportPrompt(template, { built, avfl, e2e, conflicts }),
                               { agentType: 'momentum:tech-writer' })

return { perStory: built, avfl, e2e, conflicts, reportPath }

3.3Custom agents — yes, and they compose with schema

YESagent() takes an agentType that resolves from the same registry as the Agent tool (momentum:dev-frontend, momentum:qa-reviewer, momentum:e2e-validator, …) and composes with schema — the custom agent's hot-constitution / AGENT.md / KB system prompt gets a StructuredOutput instruction appended. So your momentum agents staff the workflow's stages directly. The routing-table resolution (momentum-tools agent resolve --touches) becomes a pre-step that emits the agent name passed into agentType.

04Replacing TeamCreate for e2e

TeamCreate existed because the original rationale was "QA briefs E2E on spec changes mid-review" — agents talking. But e2e doesn't need a conversation; it needs: validate → collect failures → fix each → re-validate → repeat until clean or cap. That's pipeline + a while loop.

  • Validator = momentum:e2e-validator as the agentType; fixes = dev agents spawned per failure.
  • The cross-agent context TeamCreate provided (spec deltas) becomes a structured handoff — passed into the validator's prompt instead of agent chatter.
  • Result: deterministic, resumable, no inter-agent coordination overhead.

Note: your current workflow.md Phase 5 already bans TeamCreate and uses individual agents — so whatever TeamCreate pain you hit, the loop replaces it regardless of which version you were running.

05Caveats worth designing for now

These bite later if ignored.

① Git mutation + autonomy + resume don't mix

Merges are the danger — a workflow can't halt for conflict resolution, and resuming a half-merged state is risky. Workflow does only clean auto-merges; returns the conflict list as data; the skill resolves conflicts with the human. Keep side-effectful git out of the deepest loops.

② Worktree lifecycle ownership

momentum:dev already creates its own worktree; AVFL strategy keeps them alive until clean. The workflow's built-in isolation:'worktree' auto-cleans unchanged ones — which fights that model. Let dev agents own worktrees; make cleanup an explicit final stage.

③ Failure handling becomes policy, not a prompt

Today Phase 3 asks Retry/Skip/Halt. A workflow can't ask — pre-encode it (e.g. one auto-retry, then mark failed, continue, surface prominently in the report). Better for autonomy, but decide the policy up front.

④ Custom-agent resolution is a pre-step

agentType takes the registered name (momentum:dev-frontend) — but your agents are selected via momentum-tools agent resolve --touches. Run that resolution first, then pass the result into agent({agentType}). Worth confirming the registry name matches what the routing table emits.

⑤ The report gets a real data model

Because the workflow accumulates structured results from every stage, the report-builder renders from complete, faithful data — not reconstructed prose. Template as a skill asset (sprint-dev/assets/hitl-report-template.html), derived from the report you've been hand-asking for. This is exactly the formalization you wanted.

06The net

Your instinct is right: workflows fit sprint-dev specifically because you've collapsed the human gates to one at the end. The development-to-validated-branch span becomes autonomous workflow territory with three nested validate-fix loops; the HITL bounce-back stays in the skill as the outer human loop.
