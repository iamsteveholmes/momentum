Conduct Design · Skill Development vs Code Feature

One Pipeline, Routed by change_type

Conduct runs every story through the same per-story pipeline. What differs between developing a skill and a code feature isn't the shape — it's the routing at four points: how the story is created, which dev specialist runs it, what the verification contract looks like, and which driver verifies it. Grounded in DEC-029 (method-routed verification), DEC-023 (the agent routing table), and the spec §7 contract handoff.

01The four fork points

A single signal drives all four: the story's change_type. Planning maps it to a closed verification_method enum (precedence-weighted), and the routing table maps it to a dev specialist. Everything else is deterministic.

① CREATE-STORYEDD vs TDD guidancecreate-story injects eval-driven guidance for skills, test-driven for code; ACs are framed as skill behaviors vs runtime behaviors.
② DEV SPECIALISTrouting-table resolveagent resolve --touches picks a specialist variant of dev — not a different skill.
③ CONTRACT FORMATmethod → contract fileverification_method selects the contract's shape: an eval, a smoke script, a Gherkin feature, etc.
④ VERIFIER DRIVERmethod → driverthe harness routes the method to the driver that runs it: Skill, cmux/bash, Maestro, curl…

03The answers to your specific questions

  • How are stories created differently? Same skill (momentum:create-story), but it injects EDD guidance for skills (the eval is the spec) vs TDD for code, and frames ACs as skill behaviors vs runtime behaviors. The story's change_type is the switch.
  • Does dev use a different skill? No — a specialist variant of the same dev base. The routing table (agent resolve --touches) picks momentum:dev-skills for skill work, dev-frontend/dev-build/etc. for code. They share the dev base body (DEC-020/026); the specialist layers stack-specific knowledge. Under DEC-035, dev stays a pure builder and the same body is invoked in "fix-mode" for fixes.
  • How does verification differ? This is the real divergence (DEC-029 method-routing). The story's verification_method enum selects both the contract format (③) and the driver (④): a skill is verified by invoking it (.eval.yaml via the Skill driver); code is verified by running it (.smoke.sh/.feature via bash/Maestro/curl). QA (⑥) and E2E (⑪) both follow that routing.
  • What's identical? code-review (bmad-code-review on the diff), the fix mechanism (directed dev), merge, AVFL-on-merge, and the single end-gate report. The pipeline shape never changes.
The one-line model Conduct is change-type-polymorphic: one pipeline, with change_type → (EDD/TDD story shape · dev specialist · verification_method → contract format + driver). A skill is invoked to verify it; code is run to verify it. Everything else is shared.

Note for the first conduct sprint: all 18 stories build conduct itself in this markdown/bash repo, so they're all skill/agent-definition stories on the left lane — verified by skill-invoke evals, built by dev-skills. The code lane only lights up when conduct later runs in a code project.
