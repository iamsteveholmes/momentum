# Product Truth Lens — Nornspun Delivery Discovery

**Date:** 2026-08-02
**Role:** What is nornspun SUPPOSED to do, and what does its own paper trail admit exists? This lens reads planning artifacts (PRD, product brief, epics, roadmap, feature registry, assessments, decisions) as evidence and cross-checks their claims against each other and against the sprint-2026-07-13 build record.

---

## Executive Summary

1. **The MVP has a precise, quotable definition** — "campaign init → adventure ingestion → session prep → post-session capture → living memory → campaign identity," gated as "Friends & Family Ready" (`prd.md:547-548`). This is not the "no stable definition" finding the working hypothesis expected — see Surprises.
2. **Sprint-2026-07-13 IS the roadmap's Sprint A**, verbatim — all 12 story slugs in `mvp-roadmap-sprints-a-e-2026-07-09.md` match `sprints/index.json`'s `active.stories` exactly. Sprint A was explicitly the "keystone sprint" whose job was to lay the memory foundation the rest of the MVP gate depends on.
3. **The sprint's own end-gate report admits its core promise failed under a live model**, in its own words: *"the sprint's core promise, 'what you tell Urd gets remembered,' is not yet reliable when a real language model drives it"* — ~5 of 7 live captures produced zero database rows despite Urd's confident "It is written." receipt (`sprint-2026-07-13-endgate-report.html`, D5). This is a first-party admission, not an inference.
4. **All 12 stories shipped-merged per the end-gate, yet neither code repo's `main` branch contains any of this sprint's work.** `nornspun-backend` main is 1 ahead / 26 behind `sprint/sprint-2026-07-13`; `nornspun-client` main is 0 ahead / 27 behind. `sprints/index.json` still shows the sprint as `"active"`/`"locked"`, and every story in `stories/index.json` is `status: "review"`, not `"done"`. Whatever the developer opened, it structurally could not have contained Store A/B, episode segmentation, session naming, or the live campaign picker unless they ran the sprint branch directly.
5. **`features.json` — the single canonical feature-status tracker — has not been updated since the morning of 2026-07-13**, before the sprint that built the memory backbone even started. Every entry's `notes` field describes a pre-Sprint-A world ("Store A ABSENT — the keystone unblock," "ZERO client ledger UI") that the sprint's own end-gate report contradicts (Store A: "shipped-merged," "Executed live incl. DB verification"). No one has reconciled the tracker to the build.
6. **The product definition has changed underneath in-flight work at least twice with real blast radius**: SDR-011 (2026-05-22) rejected the 5-phase campaign-init wizard outright, and `features.json` + ASR-006 confirm the wizard's Kotlin canvas files "were built then deleted" (build artifacts confirm); SDR-014 (2026-05-31) redefined what a "session" even means (conversational "episode" vs. numbered game "session"), invalidating the in-flight `client-conversation-history-persistence` design and re-routing all downstream capture/prep/re-entry work through a new episode model that Sprint A exists to build.
7. **ASR-006 (2026-06-16) independently found and named the same story-vs-functionality gap this investigation is chartered to test**, for the *previous* six weeks of work: "every entry `last_verified: 2026-05-03`; multiple 'done'/'working' claims are wrong" — e.g., a recap-generation story counted as done in `features.json` was actually `status: draft` with a blank dev record, and "Living Memory ledger" had "ZERO client ledger UI" despite backend stories reading as complete.
8. **The end-gate report itself defaults to shipping past the unresolved gap**: its own recommended resolution for D5 (captures narrated but not saved) and D6 (one capture saved with another campaign's fabricated content, reproduced 2/2 under concurrent load) is "Approve the merge as-is" with a hardening story "next sprint" — i.e., the process's designed response to catching its own core promise not working is to ship the merge and defer the fix, not to hold the gate.
9. **Fifteen-plus tracked "stories" in `features.json` were phantom slugs with no story file at all** (ASR-006 F3), several counted toward "stories_done" ratios anyway — the feature registry's completion arithmetic was partly counting work that never existed as a schedulable unit.
10. **No planning artifact was updated to reflect Sprint A's outcome before this investigation began**: the Sprint B–E roadmap (`mvp-roadmap-sprints-a-e-2026-07-09.md`) has exactly one commit since creation and still assumes Sprint A's memory backbone is simply available for Sprint B to build on top of, without incorporating the D1–D6 residuals or the un-merged-to-main state.

## 1. The Intended MVP — Precisely Stated, With Its Own Roadmap Mapping

The PRD is unambiguous about what "the simplest things a user should be able to do" means for MVP. Quoting `docs/planning-artifacts/prd.md:547-548` in full:

> **MVP Gate: Friends & Family Ready**
> After POC 5, the product supports: campaign init → adventure ingestion → session prep → post-session capture → living memory → campaign identity. A friend can onboard their own campaign and get genuine value from the session loop — without Foundry VTT integration.

The PRD further specifies five POC milestones (`prd.md:512-545`) that build toward this gate: POC1 "Urd Speaks" (agent foundation), POC2 "The Norns Collaborate" (persistence + SSE), POC3 "The App Exists" (client), POC4 "Prep and Capture" (the session loop — Verdandi prep, Urd capture, ingestion, living memory basics, recap generation), POC5 "It Knows My Campaign" (campaign flavor, NPC/PC tracking, cross-agent memory).

This maps directly onto the epic taxonomy in `epics.json`: `agent-foundation` (POC1, `current_state: "done — all 13 stories complete"`), `local-data-platform` (POC2, in-progress), `fantasy-client` (POC3, in-progress), `session-loop` (POC4, "5 stories done, 11 backlog" — **stale**, see §3), `campaign-intelligence` (POC5, "backlog — 13 stories, none started"). `cloud-platform`, `user-accounts`, `content-creation` (Skuld/Foundry export), and `ios` are explicitly **post-MVP** (`epics.json` `cloud-platform.current_state`, `content-creation.current_state: "backlog — 8 stories, none started (post-MVP)"`).

The most recent re-sequencing, `docs/planning-artifacts/mvp-roadmap-sprints-a-e-2026-07-09.md`, adopted by the product owner 2026-07-09, re-cuts the remaining ~38-story MVP gap into five ~10-story sprints (A–E) and states the gate again verbatim: *"Campaign init → adventure ingestion → session prep → post-session capture → living memory → campaign identity — 'Friends & Family Ready,' without Foundry VTT integration."*

**Sprint-2026-07-13 is Sprint A, exactly.** Comparing the roadmap's 12-item Sprint A table (`mvp-roadmap...md` "Sprint A — Memory foundation (12 stories)") against `sprints/index.json`'s `active.stories` array: both list, in the same content, `migrate-desktopapp-tests-from-kotlin-test-to-kotest`, `exchange-id-rename-across-norn-agents`, `episode-transcript-persistence-store-a`, `episode-auto-segmentation-boundary-model`, `episode-close-summarization-store-b`, `session-naming-two-message-close`, `urds-post-session-capture`, `session-counter-live-update-on-capture-close`, `campaign-picker-get-campaigns-client-repo`, `backend-active-campaign-name-injection-fix`, `urd-threshold-flowrow-inline-prose-fix`, `norn-greeting-capability-menu-trim`. The roadmap itself calls `episode-transcript-persistence-store-a` "**Keystone**" and frames the whole sprint as "The keystone sprint" whose "Standing constraints" bind every later sprint — Sprint A was explicitly planned as the sprint that makes the rest of the MVP gate buildable.

**Roadmap's own standing constraint, worth quoting because it foreshadows exactly the failure the end-gate later caught:** *"Test-infra first: desktop tests silently did not execute in sprint-2026-06-18 (missing JUnit runtime — ~29 files never ran under CI-green)."* The roadmap already knew, going into Sprint A, that a prior sprint's green test suite had been an illusion. The end-gate for Sprint A (§2 below) caught the *same class of defect recurring inside Sprint A itself* — the Kotest-migration story's own proof-case file was still silently skipped even after the fix meant to guarantee it couldn't be (see §2, "high-risk divergences").

## 2. What the Sprint's Own End-Gate Report Admits

`.momentum/handoffs/sprint-2026-07-13-endgate-report.html` is the authoritative, developer-facing record of Sprint A's outcome. Its hero statement (verbatim):

> "All 12 stories built and merged — and the live verification run then caught the thing that matters most: the sprint's core promise, 'what you tell Urd gets remembered,' is **not yet reliable when a real language model drives it**. Three related live findings (sessions minted without play, captures narrated but never saved, and one capture saved with the wrong content entirely) all sit at the same seam: whether the model actually calls its save tools when it says it did."

Its §06 "How done is this, really?" table names "Capture reliability under a live model (D5/D6)" as **Still hollow**, with the plain-language gloss: *"Until the hardening story lands, treat 'It is written.' as unverified — a narrated capture may not be saved, and one saved record was outright wrong. This is the gap that matters."*

The specific decisions in §04 quantify this precisely:

- **D4** — "Ordinary conversation mints fake 'sessions' that count like real ones": any closed episode with no manual capture writes a numbered session row, so asking Urd a lore question can mint "Session 7" for an evening with no game played.
- **D5** — *"'It is written.' is sometimes a lie — captures narrated but never saved."* Evidence quoted directly: *"In the live verification run, Urd delivered a confident 'It is written.' close roughly seven times — and only two of those produced an actual database row. No error appeared anywhere; in one case Urd even admitted in-character that 'the binding didn't take,' claimed a retry succeeded, and still nothing was saved."* Direct DB queries: "~5 of 7 closes → zero rows; backend logs show no exceptions."
- **D6** — *"One capture saved the wrong session entirely — and replies showed other conversations' content."* Twice, a validator narrating a specific session got back content from a different campaign; once persisted (a "Graul Farmhouse" narrative the validator never spoke, silently overwriting the real session), once only in a live reply (sci-fi content in a fantasy campaign). The report flags this could be either model tool-argument fabrication or **cross-request context bleed** — a session-isolation failure — and calls the latter "the strongest finding class there is."

Notably, the report's own recommended resolution for both D5 and D6 is **"Approve the merge as-is"** with a hardening story to lead "next sprint" — the process's designed response to catching its own headline promise not working live is to ship past it, not to hold. (Whether the developer in fact chose Option A, B, or something else for D4–D6 is not recorded in any artifact this lens found — the plan-gate-decision.md for sprint-2026-07-13 only records the *pre-build* plan-gate forks, not the end-gate decision. This is an open question — see §6.)

Three of the four "unresolved coverage deferrals" table entries in §05 additionally admit that dedicated QA coverage for **Session naming**, **Urd's capture REVISE**, and **Store B summarization** was deferred to the live scenario and **did not discharge** — their acceptance behavior "remains unverified pending the D5/D6 investigation." Only `exchange-id-rename` discharged cleanly.

The report also independently surfaces a second recurrence of the exact "green suite that didn't run" failure mode the roadmap called out from the prior sprint: *"The test-migration story's own proof-case file was still silently skipped"* — even the story built specifically to guarantee tests can't silently skip had its own named proof-case (`NornApiClientChatTest`, +4 siblings, 58 tests) silently skipped until the adversarial reviewer caught it.

## 3. Cross-Check: `features.json` vs. Assessments vs. the Sprint That Just Happened

`.momentum/features.json` is the canonical per-feature completion tracker (`acceptance_condition`, `status`, `stories_done`/`stories_remaining`). Its file mtime and git history (`git log -- .momentum/features.json`) show exactly two commits: a location move, and `0b6b064 chore(momentum): reconcile features.json to ASR-006 (AVFL-verified) for the 7 MVP clusters`. The file's own `last_verified` fields read `2026-06-16` (post-ASR-006) or `2026-05-03` (features ASR-006 didn't touch) — **and it has not been touched since**, confirmed by the file's mtime (`Jul 13 10:55`, i.e., the morning sprint-2026-07-13 was planned, before any of its 12 stories were built Jul 20–22).

This means every "admitted-real" claim in `features.json` right now describes the **pre-Sprint-A** world:
- `session-prep.notes`: *"Client has ZERO prep rendering (SurfaceType enum intentionally empty)."*
- `living-memory.notes`: *"Store A (episodic transcript) ABSENT — the keystone unblock... ZERO client ledger UI."*
- `session-capture.notes`: describes `urds-post-session-capture` as still carrying the rejected AC5 binding-confirmation gate, "REVISE" pending.

The sprint-2026-07-13 end-gate directly contradicts these: Store A shipped-merged with "Executed live incl. DB verification"; the binding gate is gone (verified "gate phrasing never appeared across ~10 capture conversations"). **No one has reconciled `features.json` to the sprint that was supposed to close its biggest gap.** Anyone consulting the canonical feature tracker today would be told the memory backbone doesn't exist, when in fact a version of it was built (with known reliability defects) on an unmerged branch.

This is not a new failure mode — **ASR-006 (2026-06-16), "Design-to-Implementation Reconciliation," found and documented the identical pattern one cycle earlier**, in its own words: *"`features.json` accuracy: Stale across the board — every entry `last_verified: 2026-05-03`; multiple 'done'/'working' claims are wrong."* Concrete examples ASR-006 cites: `when-last-our-heroes-met-session-recap-generation` was counted in `stories_done: 3` for session-prep while its actual status was `draft` with "a blank dev record"; the campaign-init wizard stories were marked done in the tracker while their canvas Kotlin files were "absent" from the repo — "build artifacts confirm they were built then deleted." ASR-006 also names 15+ **phantom slugs** — tracker entries with `story_file: false`, no `.md` file — including `binding-ritual-context-summarization`, six proactive-norns slugs, six living-memory slugs, and two system-aware slugs, several of which were still counted toward per-feature `stories_done`/`stories_remaining` ratios.

**The pattern recurs on a ~6-week cycle**: ASR-002 (2026-04-12) found delivery gaps against the value vision; ASR-006 (2026-06-16) found the tracker had gone stale and partly fictional across every one of 7 MVP feature-clusters and reconciled it; and now, seven weeks later, the same tracker is stale again, this time relative to the sprint that was supposed to be the single highest-leverage unblock ASR-006 identified ("F1 — Store A is the single highest-leverage unblock").

## 4. Design Churn — Pivots, Dates, and Blast Radius on Completed Work

Two pivots stand out as having demonstrable blast radius on already-built work; a third and fourth reshaped scope without directly deleting shipped code.

**SDR-011 (2026-05-22) — "Campaign Init: Conversational Model Over Wizard."** The product owner rejected the live 5-phase sequential wizard (`CampaignInitScreen.kt`, Identity → Party Foundation → Heroes → Flavor → Session Zero) as "the wrong architecture" — *"forced sequential data-entry flow that conflicts with Nornspun's conversational voice"* — and adopted instead: a campaign name is the only required field; everything else is Urd suggesting, GM deciding. **Blast radius, per `features.json`'s campaign-init notes**: *"OBSOLETE per SDR-011 D1 (wizard): campaign-init-phases-1-2, campaign-init-screen-integration, campaign-flavor-tone-themes-and-world-personality, pc-profiles-backstory-goals-fears-and-hooks... wizard canvas Kotlin files were built then deleted — build artifacts confirm."* Four stories' worth of shipped client UI code was built, then deleted, following a decision made after they shipped. The backend schema additions underneath them were kept; the client wizard code was not.

**SDR-014 (2026-05-31) — "Session Boundary, Conversation Persistence, and Norn Resume/Greeting Model."** This decision found that "session" was structurally overloaded (a numbered game session vs. an in-memory `session_id` conversational transport concept) and that the UX spec's core promise — *"on next launch, the scroll is exactly as she left it"* — had **no backend implementation path**: *"the backend persists no transcript: `ChatRequest` carries `conversation_history` up from the client and discards it after responding. The only thing that can satisfy the spec's promise is the `client-conversation-history-persistence` story — which is in the backlog and unbuilt. The most-used path in the app is promised in design and absent in implementation."* SDR-014 replaced the ambiguous model with the "continuous relationship, auto-segmented into episodes" model, renamed `session_id`→`exchange_id`, and set up the entire episode/Store-A/Store-B architecture that Sprint A (sprint-2026-07-13) exists to build. **Blast radius**: this is a foundational re-architecture of the memory model made *after* D1–D4 (agent foundation, persistence, client, session loop v1) had already shipped stories claiming session/memory behavior — those stories' underlying model was declared wrong and superseded, not merely extended.

**SDR-015/SDR-016 (both 2026-06-16, ratified same day as ASR-006)** operationalized SDR-014 into a concrete MVP build order (episode boundary trigger, summarization timing) and separately extracted a shared `AppScaffold` chrome layer that ASR-006 found was entirely absent (no shared title bar, no picker screen, no settings screen — "every journey renders inside this shell, so its absence caps the fidelity of all of them"). These are scope-defining rather than deletion-causing, but they mean two of the seven MVP feature-clusters (`app-shell/picker/settings`, and the whole episode/memory stack) were still being architecturally decided as late as six weeks before the sprint meant to close the MVP gate.

**SDR-017 (2026-07-09)** — a "Campaign-State Manifest — Norn Load-Time Read Contract" — the most recent decision, same week as the roadmap adoption, still resolving a load-time contract question for the Norns four days before Sprint A's plan gate.

**Net effect on the roadmap's own risk register**: `prd.md`'s Risk Mitigation table (§592-608) explicitly names *"Living memory doesn't scale... test against Steve's 106-session campaign"* and *"Agent persona drifts... test with real multi-turn sessions"* as anticipated risks with mitigations. The actual failure the Sprint A end-gate caught (D5/D6 — narrated-but-not-saved captures, cross-campaign content bleed) is a different, more basic risk than either of these: not "does memory scale" but "does memory get written at all, reliably, under a real model." This risk is not named anywhere in the PRD's risk table.

## 5. Verdict — Is There a Stable, Feature-Shaped Definition of "The Simplest Things"?

**Yes, at the language level — the PRD's MVP Gate quote (§1) is stable, has not been rewritten, and precisely enumerates six journeys.** This part of the working hypothesis ("no stable feature-shaped definition exists") is **not supported** by what this lens found — see Surprises below.

**No, at the tracking-and-reconciliation level.** The artifact whose entire job is to say, feature-by-feature, "is this journey real yet" (`features.json`) has been allowed to go stale relative to the actual build not once but twice in three months (pre-ASR-006, and now post-sprint-2026-07-13), and on both occasions the staleness ran in the *optimistic* direction relative to what was later found to be true when someone actually checked (both times the correction was "this was claimed done/working and it wasn't," never the reverse). Combined with the sprint's own end-gate admitting its core promise is unreliable under a live model, and the finding that the sprint's code sits unmerged on a branch while `main` in both code repos remains at the pre-Sprint-A state — the practical, checkable answer to "can a GM do the simplest thing (talk to Urd and have it remembered)" is: **not yet, and the artifact that should say so authoritatively currently says something else, for a build that itself hasn't reached `main`.**

## 6. Counter-Evidence & Falsifiability

- **The PRD's MVP Gate is not vague or missing** — it is one of the most precisely-worded artifacts in the whole corpus, unchanged in essence since 2026-02-04's product brief through the 2026-07-09 roadmap. If the working hypothesis is "no one defined what 'done' looks like," that is contradicted directly. What is missing is *reconciliation cadence* between that stable definition and the tracker meant to report progress against it, not the definition itself.
- **The end-gate report is unusually candid, not evasive.** It does not hide D4/D5/D6; it leads with them ("Where to focus" in the hero section), quantifies them with direct DB-query evidence, and explicitly states "It does not... declare the memory loop trustworthy." A reader could argue the *process* is working as intended — catching exactly the story-vs-functionality gap this investigation was chartered to find, in the developer-facing artifact, before the developer even had to discover it themselves. Whether the *response* to that finding (recommend "approve, fix next sprint") is the right call is a separate, legitimate question this lens does not adjudicate.
- **The merge-state finding (§2, point 4) could equally be a mundane, one-off process gap** (the "approve" step of the end-gate — merge to main — simply hadn't been executed yet at the moment this snapshot was taken) rather than evidence of a systemic pattern. This lens could not determine, from planning artifacts alone, whether the developer's "couldn't do even the simplest things" reaction was formed while testing the sprint branch directly (in which case D5/D6 fully explain it) or a stale `main` checkout (in which case the explanation is procedural, not the memory system's reliability). **This would be falsified or confirmed by transcript evidence** of which backend/client checkout the developer was actually running when they formed that judgment — outside this lens's assigned artifact set.
- **A counter-reading of the "stories vs. functionality" frame**: the sprint did NOT claim all 12 stories delivered working functionality unconditionally — its own §06 table explicitly marks capture reliability, recap availability, session-counter live proof, desktop parity, and returning-player greeting as "Still hollow" *in the same document that reports all 12 stories shipped-merged*. The document is not claiming functionality it didn't deliver; it is separating "story merged" from "capability verified live" as two distinct, both-tracked facts. This is closer to the disciplined form of the practice working than a cover-up.

## 7. Open Questions

- Was sprint-2026-07-13's end-gate actually approved by the developer, and if so, on which option (A or B) for each of D1–D6? No artifact in `.momentum/` records a post-plan-gate decision file for this sprint's end-gate (only `plan-gate-decision.md`, which is pre-build). The mission brief states the sprint "finished... end-gate approved," but the repo evidence (unmerged branches, sprint still `active`, stories still `review`) does not show that approval having been executed to completion. Resolving this requires either a transcript citation (outside this lens's assigned corpus) or a later ledger/handoff artifact this lens did not locate.
- Whether the developer's negative live-testing experience was against `main` or the `sprint/sprint-2026-07-13` branch in each repo — decisive for whether D5/D6 alone explain "couldn't do the simplest things," or whether an unrelated merge/deploy gap compounds it. Not determinable from planning artifacts.
- Whether a capture-integrity hardening story (the D5/D6-recommended "top of next sprint" item) has been created: searched `.momentum/stories/index.json` and `.momentum/stories/*.md` for slugs containing both "capture" and "integrity" — no match found as of this snapshot. Whether this reflects "not yet triaged" or "triaged under a different slug/name" was not determined.
- Whether `docs/planning-artifacts/mvp-roadmap-sprints-a-e-2026-07-09.md`'s Sprint B–E composition will be revised in light of Sprint A's residuals before Sprint B is planned — the roadmap file has a single commit since creation and no evidence of revision was found, but Sprint B plan-gate materials (if any exist) were not in the file set this lens was scoped to search.
