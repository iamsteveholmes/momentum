Research Report: Gas City Human-in-the-Loop Gates and Multi-Phase Cycle OrchestrationExecutive SummaryThe transition from localized, single-session artificial intelligence coding assistants to distributed, multi-agent software factories represents a critical inflection point in modern engineering operations. Gas City, extracted from the monolithic architecture of the earlier Gas Town project, serves as an orchestration-builder Software Development Kit (SDK) specifically designed to facilitate this transition. By externalizing workflow state into persistent tracking units and decoupling execution from human interactive sessions, Gas City enables the automation of complex, multi-phase software engineering lifecycles.   As of August 21, 2026, the Gas City ecosystem operates on the stable v1.4.0 release. The introduction of the "Formulas v2" production controls has fundamentally altered how Directed Acyclic Graphs (DAGs) are evaluated, fanned out, and governed across a fleet of CLI coding agents such as Claude Code. However, fully autonomous execution is rarely desirable in production environments where security, architectural integrity, and financial burn rates are paramount. Consequently, orchestrators must provide robust mechanisms to halt autonomous execution and await human verification—a paradigm known as Human-in-the-Loop (HITL) gating.   This comprehensive analysis investigates Gas City's current capabilities for orchestrating multi-phase engineering cycles (Triage → Planning → Build → Retrospective) that rely on mandatory human approval gates. The research systematically evaluates the platform's native [steps.gate] mechanisms, the emergent engineering patterns utilized to capture human verdicts, the notification infrastructure required to alert operators, and the operational maturity of the platform and its underlying persistence layer. The findings indicate that while native declarative human gates remain partially nascent in their strict vocabulary implementation, the platform provides immensely powerful convergence mechanisms, check loops, and observation dashboards that successfully facilitate enterprise-grade human approval workflows.1. This Erlang/OTP-inspired supervision model ensures that human approvals are treated as immutable state transitions within the database, providing robust crash-recovery and auditability.   2. Gate Mechanics and the [steps.gate] PrimitiveThe orchestration of a software factory requires explicit chokepoints where automated parallel fan-outs can be halted for human verification. The [steps.gate] primitive was conceptualized to serve as this declarative roadblock within a formula's TOML definition.The Status of the Gate VocabularyAccording to the foundational Gas City specifications, the [steps.gate] table was designed to support multiple blocking types, explicitly identifying human, timer, gh:pr, and mail as valid gate types. However, forensic analysis of the current August 2026 release cycle confirms that explicit, first-class implementation of these declarative gate types within bundled community formulas remains largely limited to doc-comments and experimental branches.   There are currently zero bundled formulas shipping in the primary registry (hosted at https://github.com/gastownhall/gascity-packs) that utilize a naked type = "human" in a [steps.gate] block without relying on auxiliary convergence logic. Issue #620 specifically addresses the implementation of the "human gate (and any other step that parks sessions on human gates)," illustrating that while the framework's internal/convergence/formula.go engine parses the gate constructs, the platform relies heavily on variable-driven check loops to enforce blocking behavior safely.   The rationale for this architectural delay stems from Gas City's core design principles, specifically the mandate to "Keep judgment out of Go". The framework is designed strictly to move work, not to reason about it. A monolithic "wait-for-human" node type executed by the Go controller risks infusing the transport layer with stateful judgment logic. Instead, the maintainers favor paradigms where the human is treated identically to an agent actor, meaning the gate is simply a work unit assigned to a human that blocks subsequent nodes in the DAG.   Blocking Edges and Dependency GraphsDespite the nascent state of a dedicated type = "human" keyword, the control dispatcher inherently supports absolute blocking edges through the DAG's standard dependency graph. In Gas City, beads declare dependencies via a BLOCKS and Needs relationship.   When a formula step is dispatched, the orchestrator instantiates it as a bead within a larger tracking container known as a "convoy". If a specific bead in that convoy is assigned to a human actor, or left unassigned but tagged with a rigorous review label, the orchestrator's fan-out logic will strictly quarantine all downstream steps. The control dispatcher continuously evaluates the readiness of nodes during its reconciliation tick. Because the prerequisite bead remains in an OPEN state, the dispatcher refuses to instantiate the subsequent dependent steps.   Manual Closure and Transient Read FixesThe resolution of this blocking edge requires explicit human intervention. A human operator must manually intervene—using the command line interface (gc bd close <id>) or the visual dashboard—to transition the blocking bead's status from OPEN to CLOSED. Only upon this manual closure does the control dispatcher unblock the downstream convoy and resume the automated agent fan-out.   Historically, gates and control routing suffered from severe race conditions under heavy concurrent load, leading to dispatcher wedges. A critical architectural improvement in the v1.4.0 release is the introduction of highly resilient retry and drain mechanisms. Attempting to spawn or fan-out immediately after a gate closure no longer quarantines an in-flight run due to momentary configuration read failures. The control dispatcher will intelligently retry transient config reads rather than failing closed, which makes manually closing a human gate a significantly more reliable and deterministic operation than in the previous v1.2.x era.   3. Human Verdict and HITL Implementation PatternsGiven the architectural constraints and design philosophies surrounding the [steps.gate] primitive, practitioners have coalesced around highly specific design patterns to enforce "Approve," "Iterate," or "Reject" decisions. These patterns leverage the internal/convergence/ bounded iterative refinement loops to treat human feedback as executable state.   The Bounded Check Loop PatternThe most prominent methodology for HITL integration in Gas City is the "Check Loop," often referred to internally as the "ralph-loop". Rather than pausing a single linear step and waiting for a boolean toggle, formulas implement a bounded cycle where an agent attempts a task, synthesizes an artifact, and explicitly submits it for review.   The nature of this review converges based on launch variables passed to the formula, specifically review_mode and interaction_mode.   Autonomous Mode: An adversarial agent (e.g., a dedicated security or architectural review persona) critiques the work without human involvement.Interactive Mode: The loop exits the autonomous agent boundary and assigns a review bead directly to the human operator.   When operating in interactive mode, the human verdict is captured not just as a boolean approval, but as rich bead metadata. If the human operator rejects the proposed work, they do not simply fail the workflow; they append written feedback to the bead's description or metadata payload and reset the status to OPEN, or they generate a new sibling "revision" bead linked via the ParentID.   The convergence engine reads this verdict-as-metadata, detects the delta between the requested state and the current state, and initiates another refinement pass by the agent. The agent's next prompt is dynamically hydrated with the human's specific critique. This pattern ensures that all qualitative judgment remains localized entirely within the persisted bead state, preventing the Go orchestration layer from needing to parse arbitrary textual verdicts.   Explicit Step Assignment and Mail-to-Human ParadigmsBeyond bounded check loops, advanced multi-phase pipelines utilize the Mail subsystem for explicit out-of-band human approvals. In Gas City, inter-agent messaging—including messages directed at human operators—is constructed using the underlying bead persistence layer via TaskStore.Create(bead{type:"message"}).   When a multi-phase cycle reaches a critical, non-reversible juncture—such as a deployment readiness check, a database migration execution, or a production release—the formula generates a mail bead explicitly assigned to the human operator. The human receives this via the Dashboard's Mail interface. The subsequent formula steps are gated strictly on the resolution of this mail bead. If the human replies with an approval payload, the orchestrator detects the state change and triggers the downstream execution order.   The community pr-pipeline pack exemplifies this disciplined approach. The pack provides automated steps to map a change's blast radius and self-review outgoing pull requests against an 11-category scorecard. However, it establishes a hard, non-negotiable "pre-push gate" that strictly refuses to push code or open a PR autonomously. It mandates a manual human initiation for the final deployment step, demonstrating how packs successfully enforce safety boundaries even in highly automated environments.   4. Beads Backend Requirements and Operational CostsThe foundation of Gas City's reliability, and its ability to persist human verdicts across sessions, is its persistence layer: the Beads store. Every unit of work, mail message, formula molecule, and organizational convoy is externalized to this database.   GC_BEADS=file vs. Native DoltGas City natively supports two primary backend paradigms, each catering to vastly different operational scales.The File Backend:
By setting the environment variable GC_BEADS=file or defining [beads] provider = "file" in the city.toml configuration, operators can bypass the default database entirely. This file-based store requires zero additional dependencies (obviating the need for dolt, bd, or flock), making it highly advantageous for lightweight, ephemeral CI runs or single-user local experiments. However, it suffers from severe file-lock contention during massive agent fan-outs and lacks native query capabilities.   The Dolt Backend (Default):
For production, multi-agent, distributed orchestration, the bd (beads) provider backed by Dolt is strictly required. Dolt provides a Git-for-data Multi-Version Concurrency Control (MVCC) model, enabling transactional lifecycle semantics, bounded cached reads, and highly concurrent store-aware routing. This backend requires Dolt version 2.1.0 or newer; Gas City actively rejects older builds because releases prior to 1.86.2 lack critical upstream deadlock fixes that can hang synchronization routines under heavy write loads.   Operational Costs and Dolt Bloat Recovery (#1094)Running the Dolt backend in a production factory incurs significant operational overhead, primarily regarding storage management. The most prominent risk is severe database bloat, extensively documented in issue #1094, where a real-world installation rapidly filled a 244GB disk.   The root cause of this bloat was architectural. Working-memory artifacts generated during a formula's iterative refinement loops (e.g., highly detailed, multi-kilobyte system design prompts) were being stamped entirely into each member's user prompt during a parallel fan-out. Because Dolt tracks every granular modification with Git-like historical fidelity, duplicating a massive context payload across fifty sub-agents for every iteration loop caused exponential data bloat within the .dolt directory.   The architectural resolution involved hoisting these bulky, shared payloads into a molecule-scoped file (/artifacts/<molecule-id>/context/) written exactly once.
