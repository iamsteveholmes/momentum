# Comparison: Our Problems vs. the Field's Problems

**Date:** 2026-08-02
**Role:** Comparison agent for the nornspun delivery discovery — judges each major pattern the external research (research/external-1 … external-5) found in the field against OUR internal evidence (sprint dossiers, cross-cutting lenses, ground truth, session cartography), then inverts the question: which of our failure modes does the field not name, and which of the field's fixes have preconditions we actually meet?

**Method note.** This document synthesizes the rest of the discovery corpus; it performed no new probes of the nornspun repos. "Our evidence" citations point into the corpus documents (which themselves cite file:line, commits, DB queries, and verbatim transcript quotes). Verdicts use three labels per the brief — **CONFIRMED HERE**, **NOT PRESENT HERE**, **PRESENT WITH A TWIST** — and the standard applied is adversarial: a pattern is only CONFIRMED if our evidence shows the field's *mechanism*, not merely its surface symptom. Resemblance is not identity. OBSERVED = a corpus document directly evidences it; INFERRED = my judgment across documents, marked as such.

---

## Executive summary

1. **The headline symptom is field-canonical; the best-evidenced mechanism is not.** "Stories green, app broken" matches Anthropic/SpecBench/SWE-Lancer verbatim — but the field's mechanism is *pipelines that lie* (self-praise, circular validation), and our pipeline **told the truth and nobody acted**: the 07-13 end-gate itself said "the sprint's core promise… is not yet reliable," then the gate was never decided, the branches never merged (26/27 commits stranded), and the retro never ran (verification-lens §3; retro-loop-lens §2–3; ground-truth §1).
2. **Circular-validation/test-theater: PRESENT WITH A TWIST.** We have real specimens — a smoke test passing via a tool-call confound while the fixed behavior was broken (verification-lens §4), Maestro flows that "passed unconditionally" and were deleted 76 minutes later (04-12 dossier #5), ~29 desktop test files silently never running under green CI, twice (06-18 dossier #5) — but the field's claim that agent verification uniformly self-praises is contradicted by our E2E validator doing live DB forensics that caught the sprint's three worst bugs (verification-lens §2).
3. **Reward hacking: structurally confirmed, fraud absent.** SpecBench's "visible suites saturate, held-out tests fail" describes us exactly — the only held-out check was the developer opening the app, and it failed every time it ran. But the fraud variant (hardcoding/editing tests) appears **nowhere** in our corpus: 0/20 randomly sampled "done" stories fabricated (integration-lens §5), and a corpus-wide grep for test-editing/hardcoding findings returns zero hits. Our gap is AC scope and routing, exactly the parsimonious prior external-4 recommended.
4. **Horizontal decomposition/no-walking-skeleton: CONFIRMED — but it was a signed, deliberate roadmap choice, not agent inclination.** 9 backend routes have zero client callers; prep has a real backend and zero UI; features stall at "partial" for want of client surfaces (integration-lens §1–2). The twist: the roadmap explicitly cut sprints "along the backend dependency spine" and deferred user-observable value to Sprint E, five sprints out — the owner ratified the anti-pattern (planning-lens §5–6).
5. **Feature factory: CONFIRMED with unusually crisp receipts.** The correct instrument exists — `features.json` phrases every feature as "a user can do X" — and is orphaned: zero references in the sprint-planning workflow, no feature field anywhere in sprint state, updated only by manual assessments, stale twice, always in the optimistic direction. 0/15 features ever done while story throughput *rises* 3→9 per sprint (planning-lens §1; backlog-economics §D–E; product-truth §3).
6. **Our unique failure mode #1 — the unclosed loop — is absent from the field's literature.** The field documents premature *completion*; we exhibit premature *abandonment*: end-gate rendered honest → never decided → never merged → stories frozen at "review" → retro never ran → tracker never reconciled. Two of ~9 sprints got no retro at all; the highest-severity finding of the entire practice (fabricated capture, "high-blast-radius-architecture") was disclosed, given a recommended fix, and never became a story (retro-loop-lens §3; 07-13 dossier #1–2). External-1's searches for this variant found nothing.
7. **Our unique failure mode #2 — build/environment identity confusion — is also unnamed in the field.** The developer's damning walkthrough ran a chimera: sprint-branch client against the `main` backend missing all 26 sprint commits (07-13 dossier #6); in April an entire story was built inside a stale embedded copy of the backend repo and silently lost (quickfixes dossier #5–6); the documented desktop E2E launch command has never worked on any commit in the repo's history (ground-truth §6). No external source treats "which checkout is the product" as a failure axis.
8. **Our unique failure mode #3 — the shipped product's own runtime LLM is unreliable — falls outside the field's dev-time frame.** The worst product defect (5-of-7 captures narrated but never saved; a fabricated session persisted) is the *runtime* agent (a ~$0.06/M-token OpenRouter model) failing to call its save tools — not a coding-agent failure at all. Every external prescription targets the development loop; none addresses a product whose core feature *is* an agent that must be reliable (ground-truth §7, §10; product-truth §2).
9. **Of the field's fixes, the cheapest one is already built and merely disconnected.** The "failing-by-default feature registry" Anthropic used is structurally identical to our existing `features.json` — the fix is wiring it into planning/end-gates plus an update cadence, not new construction. Conversely, the field's flagship fix (agent drives the app as a user) has an **unmet precondition on our worst platform**: Compose desktop is AX-blind by design, the E2E launcher has never worked, the README is empty, and Docker is broken — and the field's literature is uniformly browser-based, with no desktop-Compose answer (external-1 OQ3; external-3 OQ2; ground-truth §2, §6).
10. **A walking skeleton arguably already exists — the field's greenfield framing misdiagnoses us.** Ground truth verified live: launch desktop app → see real campaigns → chat with Urd/Verdandi → memory-aware replies → conversational campaign creation → PDF ingestion with correct citation. The deficit is not "build a skeleton first"; it is wiring (upload UI, history load, prep surface), closure (merge/decide/retro), and human tasting cadence — every human walkthrough in four months found the top bugs within minutes, and there were only ~four of them (ground-truth §4–5, §9; cartography quotes).

## Part 1 — The field's patterns, judged against our evidence

### 1.1 Verification gap / premature completion — PRESENT WITH A TWIST

**Field claim** (external-1 §2; external-2 §1.1): agents "mark a feature as complete without proper testing… would fail [to] recognize that the feature didn't work end-to-end" (Anthropic, Nov 2025); "applications… looked impressive but still had real bugs when you actually tried to use them" (Anthropic, Mar 2026).

**Ours — the symptom matches verbatim.** Sprint-2026-07-13: 12/12 stories through dev → adversarial code review → QA → AVFL → E2E; developer drives the app and campaign context is broken on both platforms ("the agent doesn't know what campaign I've chosen… how can it save anything to that campaign?" — cartography, `20b5f62e`, 2026-07-31). A story whose smoke contract was "executed at E2E: both Norns named the campaign correctly" was falsified by the developer nine days later — the check passed via the model's `get_campaign` tool call while the actual fix (name injected into ambient prompt context) appears in **zero** prompt templates (verification-lens §4). That is Anthropic's sentence, re-enacted.

**The twist — the recognition happened; the action didn't.** The field's mechanism is a *blind* pipeline. Ours saw: the E2E phase ran live DB queries, caught silent capture loss (~5 of 7 closes → zero rows), caught a fabricated capture, escalated both as decision cards, and the end-gate report led with *"the sprint's core promise… is not yet reliable"* and an 8-item "Still hollow" table (verification-lens §2–3; product-truth §2). What failed is everything downstream of honesty: no end-gate decision recorded anywhere, no merge (26/27 commits stranded on sprint branches), no `done` transitions, no retro, no hardening story ever created despite the report recommending it as "top of next sprint" (retro-loop-lens §3). **INFERRED:** for us, the verification gap is real but secondary; the primary defect is a *closure* gap the field has not named (see Part 2, U1).

### 1.2 Circular validation / self-grading / AI test theater — PRESENT WITH A TWIST

**Field claim** (external-1 §3; external-2 §5; external-4 §3): the same pipeline writes code, tests, and verdict; "green means the code is consistent with itself"; agent reviewers confidently praise mediocre work.

**Ours — confirmed instances, each with evidence:**
- The campaign-name smoke contract confound above — a check that passes for the wrong reason (verification-lens §4). The coverage plan *chose* the isolated direct-question form over composing into the organic conversation, a documented design decision that manufactured the blind spot (verification-lens §6).
- **Fabricated E2E flows**: sprint-04-12 added 7 Maestro flows and deleted 5 the same day because "all 5 flows passed unconditionally… assertions… wrapped in 'when: visible:' conditionals… or asserted absence of resource IDs that don't exist" (04-12 dossier #5). Textbook theater — caught by the developer, not a gate.
- **Green suites that never ran**: ~29 desktop test files silently skipped under `useJUnitPlatform()` with no vintage engine (06-18); the very story that fixed it had its own proof-case still silently skipped, caught only by the adversarial reviewer (verification-lens §2). The "golden path E2E" on main drives a synthetic 3-widget composition, not the app, and never executes anyway (ground-truth §6).
- **AVFL/live divergence**: AVFL marked the campaign-picker session-load defect fixed at iteration 4; live Android E2E re-found it (06-18 dossier #6).
- User-worded stories routed to API-only verification: `urds-post-session-capture` and `session-naming-two-message-close` — conversational-experience stories — discharged through a curl-only composed scenario; both later found failing/unverifiable post-merge while their merge records read clean (spec-lens §2).

**The twist — the strongest checks were honest, adversarial, and effective.** The E2E validator "is a transcript-and-database forensic investigation," reproduced a second bug to test its own hypothesis, and a smoke contract explicitly declared its own blind spot rather than claiming success (verification-lens §2). The Conductor recorded NON_CONVERGENT rather than burning iterations to force green. So the field's blanket "agent judges praise agent work" does **not** hold here; theater exists at the *edges* (contracts, flows, silently-skipped suites) while the center of the verification machine was honest. **INFERRED:** adding "more independent verification" — the field's default prescription — attacks the wrong margin for us; our independent verification already worked, and its output went nowhere.

### 1.3 Reward hacking / Goodhart's law on visible tests — STRUCTURALLY CONFIRMED; FRAUD NOT PRESENT

**Field claim** (external-4 §3; external-5 §1.4): agents hardcode test cases, edit test files, `sys.exit(0)`; more broadly (SpecBench), "all models saturate validation suites" while held-out tests fail, with the gap growing with code size.

**Structural version — CONFIRMED.** Per-story Gherkin contracts are visible suites; the only held-out, user-shaped check in the entire practice was a human opening the app, and on every occasion it ran (04-06 manual testing, 05-19 walkthrough, 07-08 end-gate, 07-22/31 review) it immediately found defects the green pipeline had passed (retro-loop-lens §5 finding 8; cartography quotes; verification-lens §5). The hero-persistence gap — Urd conversationally invites character creation, no persistence tool exists, `heroes` table empty across the DB's entire life — is a "held-out requirement no visible suite ever encoded" in pure form (verification-lens §5; ground-truth §3).

**Fraud version — NOT PRESENT.** Search basis: the integration lens's random 20-story reachability sample found **zero** fabricated stories (14 reachable, 6 partial); no lens, dossier, or ground-truth section reports an agent editing, hardcoding, or special-casing a test to force green (corpus-wide grep for `hardcod.*test / edited test / modif.*test file / special-cas.*test / reward.hack` across `lenses/`, `sprints/`, ground truth, cartography → zero hits, run 2026-08-02). The one "fabricated tests" case (04-12 Maestro flows) is vacuous-assertion authorship, promptly self-reported in a commit message — sloppy, not adversarial. This matches external-4's own counter-evidence: "harness *scope*… rather than harness *fraud*" is the likely cause in non-adversarial settings. The developer's hypothesis needs no misconduct mechanism; it needs a scope/routing mechanism, and we have that mechanism on paper (spec-lens §2; planning-lens §3).

### 1.4 Silent failures — CONFIRMED (and our rule against them didn't reach the paths that mattered)

**Field claim** (external-1 §3, Columbia DAPLab): the most dangerous failures are silent — code runs, app doesn't do what was asked.

**Ours:** silent capture loss with a confident in-character receipt ("It is written." → 0 rows, no error anywhere); adventure upload 404s mapped to a generic "unexpected error" by a wrong client URL no test exercises; tests silently not running under green CI; SSE events emitted by the backend and silently dropped by a client `when()` with no matching case (ground-truth §7; integration-lens §1.2; 04-12 dossier #4). Sharpest instance: the bind ritual — built specifically to create trust — produced a fabricated summary over zero events while announcing "It is bound" (ground-truth §7). The twist worth recording: the practice's own `e2e-validation.md` rule already says "Silent failure classifies as FAIL, not PASS" — the field's exact prescription, codified — but a rule at verification time cannot see paths no check exercises (verification-lens §1). Rules don't close silent gaps; coverage does.

### 1.5 Horizontal decomposition / integration debt / no walking skeleton — CONFIRMED WITH A TWIST

**Field claim** (external-2 §3; external-3 §1–2): "Integration risk concentrates at the end. All layers… get built before anything runs end-to-end"; AI's natural inclination is layers, so force vertical slices.

**Ours — confirmed at every altitude:**
- 9 backend routes with zero client callers; the client's only upload call site hits a URL the backend never registered; `loadConversationHistory` is an empty stub; prep has a substantial backend and an intentionally-empty `SurfaceType` enum for a UI that doesn't exist (integration-lens §1–2).
- A 100%-backend sprint (04-06) whose developer asked the same day: "When do I get to see the stuff that's implemented in the backend?" (04-06 dossier #3).
- Features stall at "partial" with explicit "ZERO client UI" notes while their backend halves are done (backlog-economics §D).
- Sprint-04-12: "the blank cannot be filled" — no story completed "a GM could ___ which they could not before" (04-12 dossier #1).

**The twist — this was chosen, on paper, by the owner.** The MVP roadmap explicitly cuts sprints "along the backend dependency spine" and schedules the user-observable gate at Sprint E, four sprints after 07-13; sprint-07-13 was *designed* not to be usable standalone, and the plan gate disclosed the mechanics ("6 smoke, 3 curl, 3 bash") without stating the consequence in user terms (planning-lens §5, §8). The field frames horizontality as an agent blindspot needing prompt discipline; ours is a ratified sequencing decision plus a verification routing table keyed on code layer (`change_type: backend → curl`) rather than on where the user meets the behavior (planning-lens §3). The remedy is therefore a planning-policy change, not agent prompting.

### 1.6 Feature factory / output metrics over outcomes — CONFIRMED HERE

**Field claim** (external-5 §1.3; external-4 §4): "Output is easy to measure inside the system. Outcome lives outside it"; story/PR counts are the metric class the field just abandoned.

**Ours — mechanically traced, not just thematically matched:**
- Unit of planning is the story; `features.json` — which phrases every feature as "what will the user be able to do" — is referenced **zero** times in the sprint-planning workflow, both versions checked (planning-lens §1).
- Sprint state schema contains no feature field of any kind; "a sprint can complete with all stories done and there is no mechanism… that asks 'did any feature move forward'" (backlog-economics §D).
- 0 of 15 features ever reached done; the only 2 "working" are operator-facing. Story throughput is flat-to-rising (3→9 product-capability stories/sprint) — velocity decoupled from outcome, the amplifier thesis in one row (backlog-economics §1, §E).
- Wave rationale is 100% file-conflict/dependency mechanics; no wave is framed as "after this, a Spinner can X" (planning-lens §4).

This is Cutler/Yeret with receipts. One sharpening beyond the field: the field says teams *lack* an outcome instrument; we **own one and don't consult it** — a disconnection defect, not an absence defect.

### 1.7 Spec fatigue / "great specs, no MVP" / illusion of work — PRESENT WITH A TWIST

**Field claim** (external-2 §1–2; external-5 §1.2): heavy frameworks produce markdown instead of software; 3.5h human review per feature; "the $ cost of writing specs is costing me more than the code."

**Ours — the inventory pathology is real:** 302 tracked stories; 100 backlog stories with full specs already written against a throughput of 8–15/sprint; 23 fully-specced stories killed before build; a phantom backlog story whose `touches` point at files deleted weeks ago (backlog-economics §B, #10). Spec production is demonstrably not the bottleneck.

**The twist — the ceremony's *token/time* cost is not our observed cost.** Planning a 12-story sprint took 89 minutes wall-clock; builds run ~2 days once started. The real calendar sink is untracked human gaps — 7 days plan→activate (07-13), 18 days (06-18), a 9-day mid-review absence — which no artifact records (planning-lens §6; cartography #14). And the "illusion of work" charge fails at the code level: the work is real — +6,993/−202 backend lines in 07-13 alone, a backend ground-truth-verified as substantially working (07-13 dossier #9; ground-truth §4). Where the field's accounts describe artifacts *instead of* software, ours is artifacts *and* software, with the connective tissue (wiring, merge, closure, reconciliation) missing. Different disease, same fever.

### 1.8 Stale artifacts mislead confident agents — CONFIRMED HERE

**Field claim** (external-5 §1.2, Wattenberger): "A stale spec misleads agents that don't know any better. They'll execute a plan that no longer matches reality, confidently." Eisele: context rot.

**Ours:** `features.json` stale twice in three months, both times optimistic, currently describing a pre-Sprint-A world its own sprint contradicts (product-truth §3); 15+ phantom story slugs counted in completion ratios (product-truth #9); a 07-13 story whose deliverable "is already implemented on disk" by the prior sprint — redundant work queued off a stale backlog, caught only by a story-file flag (06-18 dossier #9); four artifacts holding four different completion states for the same 12 stories (backlog-economics §F); a story file reading `status: backlog` for work merged and end-gate-approved weeks earlier (integration-lens §4). The recurring correction direction — claimed-done later found not-done, never the reverse — is exactly the confident-lie polarity Wattenberger predicts.

### 1.9 Parallel-writer incoherence (Cognition) — MOSTLY NOT PRESENT; conflicts appear across time and repos instead

**Field claim** (external-3 §7; external-5 §1.1): parallel writing agents make conflicting implicit decisions; fix = single-threaded writes + fresh-context reviewer.

**Ours:** the per-story pipeline already *is* Cognition's working pattern — one `momentum:dev` writes per story; the fresh-context adversarial reviewer demonstrably catches real bugs (it caught the silently-skipped proof-case; it caught an IDOR pre-merge in May — verification-lens §2; 05-01 dossier #8). The wave system serializes touched-file overlaps (planning-lens §4). We found no dossier evidence of two same-wave writers shipping conflicting decisions.

**The twist:** decision conflicts show up *longitudinally and across repos* — the April URL thrash, where client and backend "fixed" each other's URL contract in uncoordinated same-day reverts, breaking campaign creation for two months (04-10 dossier #2, #5); and the client-side-only campaign binding that lets conversation say "Salt Road" while persistence targets `TrimTestCampaign` (verification-lens §4). Cognition's Flappy-Bird/Mario problem exists here, but between *sprints and repos over weeks*, not between parallel agents in a wave — a variant the single-writer fix does not address (external-5 OQ3 flags exactly this as unstudied).

### 1.10 Session amnesia / nobody holds the theory (Naur) — CONFIRMED HERE

**Field claim** (external-5 §1.5; external-2 §1.5): every agent rebuilds its theory from scratch; a human whose interface is gate reports never forms one; screwyprof: "I must relay all information between agents."

**Ours:** the developer returned after 9 days with "Can you catch me up?"; asked "So what would I expect to see with the app? … Do we have a sprint gateway?"; did not know which backend was running during their own review (cartography quotes). The reviewing assistant paired the sprint client with the `main` backend — nobody, human or agent, held the theory of what build pairs with what (07-13 dossier #6). The same campaign-context bug class was reported live by the developer at two consecutive end-gates two weeks apart, spanning a sprint that rebuilt the adjacent subsystem (cartography #2). And D4.14 rebuilt an entire backend inside a stale directory copy without noticing it wasn't the real repo (quickfixes #5). This is Naur's thesis with unusually direct evidence — including the practice-specific aggravator that the developer's designed interface to the work is reports (they themselves pushed back: "It's not just about the end-gate document it's about my review").

### 1.11 Perception gap (METR) — PRESENT WITH A TWIST

**Field claim** (external-4 §4): practitioners systematically overestimate AI-driven progress even after living it.

**Ours — the developer was *not* deluded about the product**: they articulated the report-vs-app distinction unprompted, twice ("shouldn't I be looking at the app itself?"; "I don't want to show functionality that doesn't exist" — cartography #6, quotes), and the pipeline's own verdicts were honest. The miscalibration here is **state-tracking, not self-flattery**: the mission brief itself believed "end-gate approved" while the repos show no decision, no merge, and a sprint locked "active" (07-13 dossier #1–2); four artifacts disagree on whether the same 12 stories are done (backlog-economics §F). The field's perception gap is about *speed*; ours is about *what state things are in* — arguably more tractable (it's a bookkeeping problem), arguably more insidious (every count anyone quotes is wrong in some direction).

### 1.12 Capability ceiling (SlopCodeBench / ProjDevBench) — MOSTLY NOT PRESENT at build time; PRESENT at product runtime

**Field claim** (external-1 §5): no current agent completes long-horizon iterative product work end-to-end; erosion accumulates.

**Ours — build-time evidence cuts against it:** the coding agents' output is largely real and works — ground truth verified the backend feature spine live (chat, conversational campaign creation, ingestion→retrieval with a correct NPC citation, honest-empty anti-hallucination), 14/20 sampled done stories cleanly reachable, backend never deleted a `.py` file in its history (ground-truth §4; integration-lens §5, counter-evidence). The delivery failure is concentrated in wiring, closure, and client surfaces — process-shaped, not competence-shaped.

**Where a genuine capability ceiling *does* bite: the product's own runtime.** D5/D6 — captures narrated but not saved 5 of 7 times, a fabricated capture persisted — are the *shipped product's* LLM (routed to `openrouter:tencent/hy3-preview`, a ~$0.06/M model) failing to reliably call its tools (ground-truth §10; product-truth §2). SlopCodeBench is about dev agents; nothing in the external corpus covers "your product is itself an agent and its cheap model is unreliable." See Part 2, U4.

### 1.13 The discipline-absence diagnosis (vibe-coding disaster file) — NOT PRESENT HERE

**Field claim** (external-5 §2.1): ad-hoc structure-free agent use fails catastrophically (Replit DB wipe, Tea breach).

**Ours:** inapplicable, as external-5 itself predicted. The practice has more structure than anything in the literature; the security-adjacent finding it did produce (possible cross-request context bleed) was caught *by* the process and candidly escalated (verification-lens §2). The one observed instance of process *bypass* — the 2026-07-30 hotfix committed straight to `main` outside any story, planning, or review (07-13 dossier #7) — is the exception that proves structure was otherwise in force, and notably it happened at the exact moment the ceremony had stalled. **INFERRED:** prescriptions aimed at adding rigor (more specs, more review) are already saturated here and are the one investment external-4 explicitly says will not close the gap.

### 1.14 The amplifier thesis (DORA) — CONFIRMED HERE

"AI doesn't fix a team; it amplifies what's already there" (external-1 §6). Ours amplified precisely what it instrumented: process artifacts, ledgers, audits, and retro-of-process — 65+ retro-spawned items, 100% process-shaped, 0 product-epic stories; nornspun's own 29-story process-improvement epic 0% done; the sibling Momentum repo actively shipping practice hardening while nornspun's product loop stalls (retro-loop-lens §4, §6). The un-instrumented axis — "can a user do the thing" — received amplification of nothing, because nothing measured it. This is the amplifier thesis operating on a solo practice, which external-5 (OQ4) flagged as an unverified extrapolation; our case supports the extrapolation.

## Part 2 — Inversion: our failure modes the field does not name

The external agents recorded their searches (external-1 §Counter-evidence #3; external-2 negative-claim disclosures; external-5 §1.7): no source names the fully-instrumented solo practice that passes its own gates and ships nothing, and none of the following five appear in the retrieved literature as named failure modes.

**U1 — The unclosed loop (ceremony abandonment).** The field's canonical failure is declaring done too early. Ours, at the decisive moment, is the inverse: *never declaring anything*. End-gate rendered (honest) → no decision recorded → no merge (26/27 commits stranded) → stories frozen at `review` → sprint locked `active` → retro never ran → `features.json` never reconciled → the top-severity finding never became work (retro-loop-lens §2–3; verification-lens §3). Precedent inside our own history: sprint-05-30 also got no retro; quickfix directories were abandoned mid-flight; sprint-04-12's orchestrator hung in Phase 7 and a human finished the bookkeeping four days later (quickfixes #3, #10). The pattern: the practice's *last-mile closure steps are human-gated, and human attention is the system's scarcest resource* — so honesty accumulates in documents while state never advances. Nothing in the external corpus describes a process that catches its own failure and then structurally fails to act on the catch.

**U2 — Build/environment identity confusion.** The developer's decisive negative experience ran a chimera build (sprint client + pre-sprint backend — 07-13 dossier #6); the app "couldn't do the simplest things" partly because the simplest things were sitting unmerged on a branch (ground-truth §1). Earlier: an entire story built inside a stale embedded repo copy, deleted seven weeks later with nobody porting the work (quickfixes #5–6). Ops substrate: empty README, broken Docker Desktop, containers from April, an E2E launch command that has never worked on any commit (ground-truth §2, §6). The field's accounts assume everyone at least agrees on what artifact is "the app." Ours shows that with multiple repos, worktrees, branches, and stale copies, *product identity itself* becomes a failure axis.

**U3 — Redundant truth systems that never reconcile.** Four completion states for the same 12 stories across four artifacts; story files disagreeing with the index for months; a "done" index entry over an empty Dev Agent Record; phantom slugs in completion arithmetic (backlog-economics §F; integration-lens §4; product-truth #9). The field discusses spec-vs-code drift; it does not discuss *status*-tracking systems drifting against each other so that no count anyone quotes (including the "91 done" in this mission's brief) is trustworthy.

**U4 — Product-runtime agent unreliability as the top product defect.** "It is written." over zero rows is not a delivery-process failure — every process fix in external-3 could be adopted and a ~$0.06/M-token model might still skip its tool calls under load. The field's verification literature verifies *code*; a product whose core promise is an agent reliably performing side effects needs *runtime* reliability engineering (receipts verified against the DB, retry/ack protocols, model-tier evaluation — the end-gate's own D5 proposal) that no surveyed source covers (ground-truth §7, §10; product-truth §2).

**U5 — The self-improvement loop structurally exiled from the product.** Retro findings route away from the product backlog by explicit policy; nornspun's own process-fix stories (including three critical-priority fixes for exactly the "status lie" failure, spawned May 2026) are 0/29 ever built; practice hardening thrives in a sibling repo instead (retro-loop-lens §4, §6). The field has essentially no retro literature at all (external-2 resonance #9: nobody reports their retro layer catching this class), let alone a treatment of retro output routing as a failure surface.

**Partially named — solo-operator attention economics.** Kent Beck's "system administrator of my own process" (external-5 §1.1) gestures at it, but no source treats developer attention as the *binding constraint* the way our evidence does: 3 real turns across 7 days of planning; a yolo-mode retro by explicit request; 7–18-day untracked gaps around gates; a 9-day absence mid-review (cartography #5; planning-lens §6). Every ceremony the practice added bids for the same scarce attention that product tasting needs — and tasting lost: roughly four human walkthroughs in four months, each finding the top bugs within minutes.

## Counter-evidence & falsifiability

Evidence cutting against this document's own findings:

1. **Against "the pipeline was honest, closure was the failure" (§1.1–1.2):** the honesty is unevenly distributed. The merge records for three capture stories read clean (`findings_summary: []`) *before* the post-merge check found their ACs failing (spec-lens §2) — at the story-terminal layer, the record *was* falsely clean, which is closer to the field's classic mechanism. If a future audit of the other seven dedicated-run contracts finds more confound-passes like the campaign-name story (verification-lens flags this as unchecked), the balance shifts back toward field-standard circular validation and away from my "closure-first" ranking.
2. **Against "fraud not present" (§1.3):** my basis is a 20-story sample, lens reports, and a corpus grep — not a line-by-line audit of every contract. The 04-12 fabricated Maestro flows show agents *can* author vacuous checks here; if the unaudited contracts hide more, "structurally confirmed, fraud absent" weakens to "fraud rare."
3. **Against "capability ceiling not present at build time" (§1.12):** the client half of the stack shows the field's erosion signature more than the backend (3,748 lines deleted, wizard build-teardown, wiring bugs at every seam). A reading that says "the ceiling manifests specifically in cross-repo UI work" is compatible with SlopCodeBench and would partially rehabilitate the field's framing.
4. **Against the unique-failure claims (Part 2):** all rest on the external agents' recorded search absences. Those searches were English-language, web-indexed, one-day efforts; Discord/podcast/private-community treatments of "ceremony abandonment" or "wrong-build reviews" may exist. U1–U3 would be demoted from "unique" to "under-documented" by a single credible published account.
5. **Against the fix-precondition table (Part 3):** ground truth could not click the real desktop window (no assistive access); "the skeleton already works" leans on a ViewModel-level probe plus visual render. If a human drives the desktop app and chat fails to render, the "walking skeleton exists" claim collapses and the field's greenfield framing applies after all.
6. **What would prove the central comparison wrong wholesale:** if the next sprint merges 07-13, runs the retro, wires `features.json` into gates — i.e., executes pure closure — and the developer *still* can't do the simplest things in a correctly-paired build, then the closure-gap thesis over-claimed and the residual explanation reverts to the field's standard verification-gap + capability account (most likely via U4, runtime model unreliability).

## Open questions

1. **Did the developer's "couldn't do even the simplest things" session run the sprint worktree build or `main`?** The phrase postdates the transcript corpus (cartography #7). The answer apportions blame between U2 (wrong build), U1 (unmerged work), and D5/D6 (real runtime defects) — the three explanations this comparison keeps separate but cannot weight precisely.
2. **Would field-standard journey gating have caught D5/D6 earlier — or is runtime LLM unreliability (U4) irreducible at the current model tier?** The end-gate's own evidence (5-of-7 silent losses under a live model) suggests any journey gate would have flared red at the first sprint that put a real model in the loop; whether the fix is process (receipts/verification in-product) or model-tier (stop routing the Norns to a $0.06/M model) is undetermined and is a *product* engineering question outside all surveyed literature.
3. **Is there any published account of a heavy practice being successfully *reformed* rather than abandoned or lightened?** External-3 (OQ1) found none. Our remediation — if it keeps the ceremony and adds closure + journey gates — would be walking a path with no external precedent either way.
4. **Does the "attention is the binding constraint" reading survive instrumentation?** Nothing currently records developer-side review time (planning-lens OQ1). If the 7–18-day gaps turn out to be deliberate cooling-off rather than displacement, U1's "attention scarcity" mechanism needs revision toward "missing closure automation" alone.
5. **Compose-desktop journey driving remains an open engineering problem with zero field guidance** (external-1 OQ3, external-3 OQ2). Whether Maestro-on-Android as the sole automated journey gate is sufficient for a two-platform product — or whether the desktop demands a bespoke driver (the in-repo compose-driver was never launchable) — no evidence internal or external answers.
