# manifesto-builder skill (generate-then-curate)

## Story

As a developer,
I want a standalone `momentum:manifesto-builder` skill that produces an agent's manifesto — the
per-role×domain diagnostic table (observable symptom → exact `wiki-query`) plus its stack facts and
its normative `## File Ownership` glob list — by auto-drafting entries from the project KB and then
requiring me to curate the symptom phrasing,
so that building an agent means authoring its diagnostic identity: reusing the KB-generation method
while preserving the human-curated symptom quality the recovered prototype proved is the valuable part,
and producing on disk the `.claude/manifests/{role}-{domain}.md` input files that `build-guidelines`
already expects but which nothing currently generates.

## Description

Per DEC-038 D1, the manifesto **is** the agent's diagnostic table (observable symptom → exact
`wiki-query`, scoped by stack facts). This story builds the **producer** for that file. Today the
pipeline has a hole: `build-guidelines` Phase 1 *discovers* manifesto files at
`.claude/manifests/{role}-{domain}.md` and validates their required sections, and `agent-builder`
*composes* a manifesto that is handed in — but **no skill authors one**. Ground truth (verified
2026-07-06): zero manifesto instances exist anywhere (`.claude/manifests/` is absent in both Momentum
and nornspun). This unset input is what blocked the live gen-2 agent run — the missing producer this
story delivers.

**Two open questions the stub carried are now resolved (recorded here as the story's design stance):**

1. **Standalone vs. folded-into-agent-builder → STANDALONE.** This is a new
   `skills/momentum/skills/manifesto-builder/` skill — the epic's value analysis names it
   ("Generated by manifesto-builder (new skill)"). Note the epic's separate "build-guidelines
   orchestrates both constitution-builder and manifesto-builder" framing is **aspirational and
   superseded by the as-built workflow**: `build-guidelines/workflow.md` is discover-only — it
   invokes `agent-builder` (and optionally `constitution-builder`) and *consumes* manifesto files
   from `.claude/manifests/` on disk; it never authors them and never invokes their producer. So
   manifesto-builder is a **developer-invoked** producer that runs **before** build-guidelines in the
   composition sequence, leaving the manifest files on disk for build-guidelines to discover.

2. **DEC-038 Gate G2 (authored vs. generated) → GENERATE-THEN-CURATE.** The skill auto-**drafts**
   diagnostic-table entries from the project KB (reusing `constitution-builder`'s Phase 3
   `wiki-query`-per-concept loop), then routes the draft to the developer to **curate** the symptom
   phrasing. Rationale (DEC-038 D1): the recovered `cmp-dev` prototype proved the quality of symptom
   phrasing — specific, observable, diagnostic — is the expensive, valuable, human-designed part;
   generation seeds it, curation perfects it.

**Re-enrichment note (why this story was re-fleshed):** the prior spec predated the normative
`## File Ownership` field (specified by `manifesto-format.md` + PRD FR136, added 2026-07-06). This story is
grounded in the CURRENT format spec — `skills/momentum/references/manifesto-format.md` (v1.0) — whose
`## File Ownership` section is now a **required, machine-readable** field that `build-guidelines` reads
*verbatim* as the composed agent's `agents.json` `patterns[]`. The only worked exemplar
(`docs/research/manifesto-cmp-dev-exemplar-2026-06-16.md`) **predates that field** and must not be
copied blindly: it is a format reference for the diagnostic-table shape only, never a Momentum
manifesto, and it carries no File Ownership section.

Source: DEC-038 (Manifesto as Per-Agent Diagnostic Table + Per-Project Multi-KB Architecture,
2026-06-16), Gates G1/G2. Format authority: `skills/momentum/references/manifesto-format.md`.
Background: `.momentum/handoffs/manifesto-cmp-dev-recovery-2026-06-16.md`.

## Acceptance Criteria

1. **Standalone skill package exists and conforms to skill conventions.** A new skill lives at
   `skills/momentum/skills/manifesto-builder/` with a `SKILL.md` (and `workflow.md` if the body
   exceeds the line budget). The `SKILL.md` frontmatter carries a `description` ≤150 characters,
   `model:` and `effort:` fields, and the skill is addressable as `momentum:manifesto-builder`.
   (Observable: the skill can be invoked by name and its frontmatter passes NFR1/model-routing checks.)

2. **Produces a format-conformant manifesto at the canonical path.** Invoking the skill for a given
   `role` × `domain` produces a manifesto file at `.claude/manifests/{role}-{domain}.md` containing —
   in the order the format spec requires — (a) a YAML identity block with `role`, `domain`, and
   `project_kb`; (b) a `## Project Stack` section with the stack facts that scope the lookups;
   (c) a `## File Ownership` section; (d) a `## Diagnostic Table` section.
   (Source: `manifesto-format.md` → File Location, Identity Block, Project Stack, File Ownership,
   Diagnostic Table, Manifesto File Template.)

3. **Generate step auto-drafts the diagnostic table from the project KB.** The skill draws draft
   symptom→`wiki-query` entries by running the `constitution-builder` Phase 3 method — read the KB
   `index.md`, then `wiki-query [concept]` (or `wiki-query --kb [project] [concept]` in multi-KB
   mode) per technology area/concept of the role×domain — and renders each result as a
   `- **<symptom>** → \`wiki-query <exact terms>\`` bullet grouped under `###` technology-area
   headings. (Observable: for a role×domain with a reachable KB, the draft contains multiple grouped
   entries whose terms trace to KB concepts, not invented ones. Source: `constitution-builder` SKILL.md
   Phase 3; `manifesto-format.md` → Diagnostic Table Section, Grouping.)

4. **Curate step requires human refinement of symptom phrasing before finalize.** After generating the
   draft, the skill presents the diagnostic table to the developer and elicits curation of the symptom
   phrasing (and File Ownership globs) before writing the final file. The skill does not silently
   finalize a generated draft as if it were curated. (Observable: an interactive curation exchange
   occurs between generation and the final write. Source: DEC-038 G2 + D1 rationale.)

5. **Symptom phrasing and `wiki-query` invocations obey the normative rules.** Every finalized entry's
   symptom is observable, specific, diagnostic, and phrased as a situation (not a question), and every
   entry supplies an **exact** literal `wiki-query <terms>` invocation rendered in backticks — never
   "search for X" or a "consult KB if needed" placeholder. (Source: `manifesto-format.md` → Symptom
   phrasing rules (normative), wiki-query invocation rules (normative).)

6. **File Ownership is authored fresh as a non-empty, concrete glob list — never omitted, empty, or
   over-broad, and never copied from the exemplar.** The produced `## File Ownership` section declares
   a `file_ownership` YAML list of glob strings that is: non-empty (an empty list equals a missing
   field); concrete enough that each glob matches at least one real file the agent would touch; in
   standard glob syntax; inclusive of every file type the agent routinely edits; and not reduced to a
   single over-broad `**/*` unless the agent genuinely owns the whole tree. Because the exemplar
   predates this field, the list is derived from the role×domain's actual owned paths, not lifted from
   the exemplar. (Source: `manifesto-format.md` → File Ownership Section (Required), normative
   authoring rules; PRD FR136 File Ownership field.)

7. **Output is complete and passes build-guidelines Phase 1 Discover validation.** The produced
   manifesto satisfies the format spec's Completeness Criterion — it covers every technology area and
   situation the role routinely encounters, with no obviously un-routed area and no "DRAFT"/placeholder
   residue. Completeness is **qualitative, not a count**: entry volume is informational only and never a
   gate (for a rough sense of scale the exemplar carries 36 entries; a sparse KB legitimately yields a
   sparser draft — see the Dev Notes KB-dependency note). Consequently `build-guidelines` Phase 1 marks
   the manifesto `valid: true`: required frontmatter present, `## Project Stack` present,
   `## File Ownership` present AND non-empty, and `## Diagnostic Table` present with ≥1 entry —
   **provided a base body also exists at `skills/momentum/agents/{role}.md` for the chosen role** (Phase
   1's 5th validity check, outside this skill's control: the sprint's live-run target `dev`×`kotlin-compose`
   is unaffected since `agents/dev.md` exists, but `qa`/`e2e`/`architect`/`pm` have no base body yet).
   Under the `skill-invoke` verification method the enforced checks are the four manifesto-intrinsic
   Phase-1 checks plus the qualitative completeness criterion (by inspection); entry count is advisory
   only. (Source: `manifesto-format.md` → Completeness Criterion; `build-guidelines` workflow.md Step 1
   validation checklist, including the base-body existence check.)

8. **The design resolutions are recorded in the skill.** The `SKILL.md` states its two committed
   stances — standalone producer (not folded into agent-builder) and generate-then-curate (DEC-038 G2)
   — and cites `manifesto-format.md` as its output authority and DEC-038 as its decision authority, so
   a future reader sees why the skill exists and how it decides. (Source: stub AC "the authored-vs-
   generated design (DEC-038 G2) and standalone-vs-folded question are resolved and recorded.")

- [ ] **Task 2 — Author `SKILL.md` (frontmatter + skill body).** (AC1, AC8)
  Create `skills/momentum/skills/manifesto-builder/SKILL.md`: frontmatter (`name: manifesto-builder`,
  `description` ≤150 chars, `model:`, `effort:`); body stating the two design stances (standalone
  producer; generate-then-curate per DEC-038 G2), the canonical output path
  `.claude/manifests/{role}-{domain}.md`, and citing `manifesto-format.md` (output authority) and
  DEC-038 (decision authority). If the body would exceed 500 lines, split the phase detail into
  `workflow.md` and keep `SKILL.md` a pointer.

- [ ] **Task 3 — Specify the GENERATE phase.** (AC3, AC5)
  Define inputs (`role`, `domain`, `project_kb`, stack facts — elicited or derived) and the draft loop
  reusing `constitution-builder` Phase 3: locate the vault/KB (`cat ~/.obsidian-wiki/config`), read the
  KB `index.md`, run `wiki-query [concept]` per role×domain technology area, and render each result as
  a grouped `- **<symptom>** → \`wiki-query <exact terms>\`` bullet under `###` area headings. Also draft
  the `## Project Stack` facts and a first-pass `## File Ownership` glob list from the role×domain's
  owned paths.

- [ ] **Task 4 — Specify the CURATE phase.** (AC4, AC5, AC6)
  Define the interactive step that presents the drafted diagnostic table and File Ownership globs to
  the developer, elicits refinement of symptom phrasing (observable/specific/diagnostic/situation) and
  of the globs, and blocks finalize until curation input is received. Include the normative symptom and
  `wiki-query` invocation rules as the curation checklist.

- [ ] **Task 5 — Specify the FINALIZE/WRITE phase and self-check.** (AC2, AC6, AC7)
  Write the curated manifesto to `.claude/manifests/{role}-{domain}.md` per the format spec's Manifesto
  File Template (section order: identity block → `## Project Stack` → `## File Ownership` →
  `## Diagnostic Table`). Before writing, self-check against the Phase 1 Discover checklist (required
  frontmatter, Project Stack present, File Ownership present + non-empty, Diagnostic Table ≥1 entry) and
  the completeness criterion (no placeholder entries, no obviously un-routed routine area).

- [ ] **Task 6 — Run the EDD cycle.** (AC2–AC7)
  Execute the Task 1 evals against the authored skill; diagnose and revise instructions on any miss
  (max 3 cycles). Confirm the produced manifesto passes build-guidelines Phase 1 validation.

## Dev Notes

### Decision Authority

- **DEC-038 D1** — the manifesto IS the agent's stable per-role×domain diagnostic table (symptom →
  exact `wiki-query`), canonically "diagnostic table"; NOT a per-sprint/per-story overlay.
- **DEC-038 G2** — this story's shape (generate-then-curate) is the ratified answer to the
  authored-vs-generated gate; the developer directed it explicitly for this sprint.
- **`## File Ownership` field — authority: `manifesto-format.md` + PRD FR136** (NOT DEC-038, whose
  text never mentions File Ownership). The normative, machine-readable field is the deterministic
  source of `agents.json` `patterns[]`: `build-guidelines` reads it verbatim. Per FR136 the field
  closes DEC-038 **G1**'s ("does the pipeline actually produce a composed agent") deterministic-
  reachability residual — that linkage is FR136's framing, not DEC-038's own text. A manifesto missing
  the field is incomplete and is skipped by build-guidelines with an explicit signal.
- **DEC-038 D2** — agents/KBs are project-scoped; `project_kb` identifies the KB the entries resolve
  against; the `cmp-dev` exemplar is nornspun-only, a format reference, never a Momentum agent.

### Pipeline Ordering (where this skill sits)

`momentum:manifesto-builder` (this story: author `.claude/manifests/*.md`, generate-then-curate) →
`momentum:build-guidelines` (discovers those manifests, composes agents via `agent-builder`, registers
`agents.json`) → sprint-dev/conduct (spawn composed agents). This skill is the first, previously-missing
link. It is developer-invoked (the curate step is inherently interactive); build-guidelines does not
call it — it consumes the files it leaves on disk.

### Architecture Compliance

- Output MUST conform section-for-section to `manifesto-format.md` (identity block, `## Project Stack`,
  `## File Ownership`, `## Diagnostic Table`, completeness criterion). The format doc is self-sufficient
  — a conformant manifesto is authorable from it alone.
- `## File Ownership` is authored fresh from the role×domain's owned paths per the normative rules
  (non-empty, concrete, standard glob syntax, all edited file types, not solely `**/*`). It is NOT
  inferred from `## Project Stack` prose and NOT lifted from the exemplar (which lacks it).
- Reuse — do not re-implement — the `constitution-builder` Phase 3 KB loop for the generate step.
- No sprint/story/overlay language anywhere in the produced manifesto (DEC-038 D1).

### Testing Requirements

- **Change type:** `skill-instruction` → **EDD** (Eval-Driven Development), not TDD. Skill instructions
  are non-deterministic LLM prompts; write behavioral evals first (Task 1), implement, then run the
  cycle (Task 6). Evals test behavior/decisions, not exact output text.
- **Verification method (advisory):** `skill-invoke` — invoke `momentum:manifesto-builder` for a
  role×domain against a reachable KB and observe it (a) generate a grounded draft, (b) route to
  curation, (c) finalize a format-conformant `.claude/manifests/{role}-{domain}.md` that
  build-guidelines Phase 1 marks `valid: true`. A frozen verification contract for this sprint lives at
  `.momentum/sprints/{sprint-slug}/specs/manifesto-builder-skill-generate-then-curate.{ext}`. Before
  signaling done, dev reads only the Part-A header (`how_dev_self_checks`, `verification_method`,
  `harness_profile`) as a self-check — never the Part-B verifier body (scenarios/assertions) beyond
  what `how_dev_self_checks` references.

### KB dependency (soft — not a build blocker)

The generate step queries whatever project KB is configured; it is KB-agnostic. For this sprint's live
goal the target is the **existing nornspun fixture KB**, so the skill does not hard-depend on
`momentum-knowledge-base-buildout` (backlog, parallel work). `depends_on` is therefore empty: every
input the skill consumes — `manifesto-format.md`, the `constitution-builder` loop, `build-guidelines` —
is already `done` on disk. A sparse KB yields a sparser draft (surfaced by the completeness self-check),
not a failure.

#### skill-instruction Tasks: Eval-Driven Development (EDD)

**Do NOT use TDD for SKILL.md or workflow.md files.** Skill instructions are non-deterministic LLM
prompts — unit tests do not apply. Use EDD:

**Before writing a single line of the skill:**
1. Write 2–3 behavioral evals in `skills/momentum/skills/manifesto-builder/evals/` (create `evals/` if it doesn't
   exist):
   - One `.md` file per eval, named descriptively (e.g.,
     `eval-produces-conformant-manifest-with-file-ownership.md`).
   - Format each eval as: "Given [input and context], the skill should [observable behavior — what
     Claude does or produces]."
   - Test behaviors and decisions, not exact output text.

**Then implement:**
2. Write/modify the `SKILL.md`, `workflow.md`, or reference files.

**Then verify:**
3. Run evals: for each eval file, use the Agent tool to spawn a subagent. Give it the eval's scenario
   as its task and load the skill (pass the SKILL.md/workflow.md as context, or invoke by its Agent
   Skills name). Observe whether behavior matches the eval's expected outcome.
4. If all evals match → task complete.
5. If any eval fails → diagnose the gap in the skill instructions, revise, re-run (max 3 cycles;
   surface to developer if still failing).

**NFR compliance — mandatory for every skill-instruction task:**
- `SKILL.md` `description` field must be ≤150 characters (NFR1) — count precisely.
- `model:` and `effort:` frontmatter fields must be present (model routing per FR23).
- `SKILL.md` body must stay under 500 lines / 5000 tokens; overflow goes in `workflow.md` /
  `references/` with clear load instructions (NFR3).
- Skill name uses the `momentum:` namespace prefix (NFR12).
